## 当前交付

新核心位于 `game/rules/template/`，不根据店铺ID或旧经营模式选择执行器：

- `inventory.gd`：唯一lot/claim库存；容量与归属预留、完成拿取才进入手持、完成放下才转移目标、加工原子扣料/产出、已拿材料的返还空间、无限源及设备内建原料供给、幂等与严格恢复。
- `machines.gd`：人工/自动加工、批量装卸和中途搅拌的同一生命周期；人工工时使用全局员工手速；召回后保留已完成工作，换员工按新手速继续。
- `capability_runner.gd` / `action_context.gd`：公共RuleActions和RuleMovement执行真实移动/拿取/运输/放下/操作；同一员工容量与升级用于真实搬运，不只用于属性卡。无路保持阻塞，取消释放程序、路径与库存预留。
- `view_frame.gd`：从权威库存生成UI库存、手持、机器状态；默认库存不生成场景图片。显式`stock_showcase`端口复用货架/用餐展示，缺端口不回退为工位坐标。
- `compiler.gd` / `SpecShopTemplate`：严格的容器、设备和配方数据；显式生产者、输入输出、依赖与稳定拓扑顺序。缺分支、缺端口、循环、产量不足、未知能力/参数均报错，不接受店铺回调。
- `runtime.gd`：同一生产调度器跑线性、双支合流和并行订单；缺料等待、补料继续；保存恢复核对模板签名、图事实、机器事务、库存、角色程序和权限，失败不部分采用。
- `recipe_normalizer.gd`：制作边界的严格生产定义转换；小炒饭馆7道配方与奶茶两款/煎饼一款前台子集使用同一转换器和公共运行器。缺规则、缺资源和错误类型返回精确路径，不生成可运行的半份模板。
- `content_projection.gd`与`ShopContentContract.describe_template`：独立模板内容身份；数量、依赖、端口、容量、初始库存、槽位、归属和新增人工阶段仍是结构，明确声明的工时/评分/权重可调。未接入正式SpecShop内容采用。
- 公共 `RuleNumbers.capability_seconds` 统一新旧人工时长的数值公式；新模板的加工和补货不再依赖旧机器对象判断是否应用升级。固定工序跳过机器速度倍率，员工手速仍由公共人工阶段应用；原奶茶冻结轨迹保持一致。
- `restock.gd`：共享批量库存按阈值补货；同一组能力执行真实取料、装料、加工、搅拌和卸料。自动源可无人运行；同容器加工按实际物料释放的空间判断容量，读档不会启动第二份批次。
- `source_demand.gd`与可选`restocks.policy`：从生产事实及权威库存/claim派生未覆盖需求；基础量、需求倍率和低库存触发均为显式公共策略。缺省仍按原整批填库存规则运行；未自动采用旧奶茶未执行的stock字段。
- `batch_recipe.gd`与可选`restocks.batch`：每份配比、整锅份数和公共batch修正明确分离；搬齐整锅原料才开工，途中升级不修改旧锅claim数量，读档按合法配比/范围校验。补货取料可显式复用公共工时目标。
- 编译器的显式integrated输入绑定：配方和机器输入容器必须共同声明安装材料，缺配置不推断。有限原料真实搬运，内建原料复用原库存operation生成/消耗，不增加店铺分支或数量账本；需求投影不会为它虚构搬运。
- `orders.gd`：公共排队与接单事实、生产份数绑定、实物交付证明、收款/离队策略与幂等结算。未放下的物品不能计交付，附加品未齐不能按交付结账。现已由公共服务能力接入生产运行器。
- `customers.gd`：共用RuleMovement推进顾客排队、取餐和离店；统一170逻辑单位速度、真实抵达、暂停和恢复。缺端口报错，无路等待；顾客不能读取员工通行权限。
- 携带者能力已扩展为公共`reserve_actor_transfer`。员工与顾客各自有命名空间，复用同一预留、拿取、携带、放下、取消与守恒；顾客携带不伪装成员工，也不另建库存。
- `bundle_transfers.gd`：整组精确预留、逐站拿取、整组放下和取消补偿复用普通claim。缺配餐、容量不足或任一目标不足时不留半份预留；子项不能绕开整组生命周期。员工真实逐站取货与顾客同点整单拿取使用同一库存能力。
- 公共员工`interact`能力复用RuleActions移动和工作计时，以稳定顾客ID提交一次完成/取消结果。员工被召回时不能把“任务空闲”误判成“接单完成”。
- `service.gd` / `service_policy.gd`：服务能力已组合进`Runtime.step`；受控模板从真实到店、排队、接单、请求生产、出品/备餐、柜台/自取/送桌、结算、入座用餐走到真实出口。公共服务不读取旧经营模式或店铺ID，不安装店铺回调；默认仍不生成库存场景图标。
- 订单记录扩展座位租约、用餐剩余时间、公共加工事务的食物消耗凭据和已离店事实；顾客运动不持有第二份订单或库存。报价在接单时调用既有公共价格接口，现金与销量继续使用外层唯一RuleSales。
- 新快照交叉验证订单生产绑定、顾客动作目标、动态顾客容器、服务员工租约、整组携带和用餐凭据。接单、生产、员工拿取、顾客携餐和用餐五个时点的恢复与连续运行轨迹/收入/销量一致；恢复失败不会先修改原角色。
- 后续批次：`arrivals.gd`已组合固定/指数到店、开张顾客、加权菜单、客流倍率与暂停/关闭；满队不抽废弃菜单。`RuleSampling`与`RuleNumbers.flow_interval`抽出相同的旧公式供新旧共同调用，原奶茶冻结轨迹保持一致。客流RNG只由外层持有一次。
- 客流/岗位批次：`dispatch.gd`提供公共角色/岗位权限，对真实加工、普通与整组搬运、接单，以及推进和恢复统一检查。无资格请求不留库存/机器预留；调岗或通行区域变化先撤销旧任务并补偿物品，操作员被移走后不再贡献人工工时。该批次已提交推送`4ea4feb`。
- 本批：生产、补货、接单、备餐和员工交付共用一个排序候选池和领取循环；服务组件不再另派员工。可配置稳定分数、工序继续奖励、真实路径成本，以及`none/prefer/exclusive`订单跟随；后者能由同一员工完成主餐与配餐并交付，在三种服务组合复用。
- 本批：`dispatch_leases.gd`持有跟单身份和同一机器批次的装料/搅拌/卸料租约；自动等待可按配置协助共享杂活，召回和调岗能释放空闲员工的持有。省略owner的普通/整组请求不能偷走跟单物料，拒绝的库存候选不会被采用；scope、订单与机器身份在恢复前交叉验证。

真实动作契约使用三类现有店铺定义的受控空间，调用同一个新执行器；这不等于三家正式店已经迁移。
