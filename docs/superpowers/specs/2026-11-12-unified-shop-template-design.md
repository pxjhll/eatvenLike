# 全店铺公共能力与模板运行体系

日期：2026-11-12。核查基线：`0717c08`，分支 `codex/tea-baseline-shared-staff`。

状态：用户已于2026-11-12以“开始吧”确认本设计并授权实施。实施按U01–U07顺序推进；本文不是实现完成报告，尚未替换正式运行路径。

## 1. 用户要求与完成定义

用户明确要求：“那就全都走模板化，不要单独行为，即便有特殊行为，也是要走公共能力添加的。”

奶茶店是基础行为蓝本。新增店铺只装配资源、空间模块、设备能力、配方依赖、岗位和经营配置。普通员工只增加全局角色定义和动作资源。已有能力不能满足需求时，向公共能力库增加实现，再由模板显式组合启用；不向某一家店增加专用执行脚本。

完成不是三个店都设置了 `action_version=1`，也不是测试总数增加。完成必须同时满足：

1. 三家正式店、制作示例店和扩展夹具共用一个运行入口、一套权威库存操作、一套机器状态、一套任务生命周期和一套表现快照。
2. 同一基础操作跨模板遵守同一语义。特殊业务只能改变声明的组合、参数或公共策略，不能重写基础操作的副作用。
3. 正式运行不再根据 `handoff/single/serve` 分流到三个经营执行循环。旧模式名只允许出现在旧定义/存档的转换器、历史夹具和迁移验证中。
4. 缺少公共能力或端口时，制作校验明确报错；不能退回旧执行器、默认角色、直线穿物或另一家店的图片。
5. 奶茶可接受行为、三店旧档续做、实际画面和公共能力复用都有独立验收证据。

范围覆盖员工、顾客、库存、机器、流水线、派活、交付、收款、取消续做、显示与制作约束。场景美术、菜单、售价、客流和最终完店时长不在本次架构工作的调参范围。

## 2. 本次核查确认的断层

| 现有位置 | 已共用的部分 | 仍然分开的部分 |
|---|---|---|
| `shop_rules.gd` / `rule_actions.gd` | 动作游标、生命周期、移动调用 | `_tick_handoff`、`_tick_single`、`ServeFlow.tick` 分别派活、提交业务结果 |
| `rule_inventory.gd` / `serve_flow.gd` | 部分机器字典、守恒检查 | 输入输出库存与 `serve.goods` 是不同的转移实现 |
| `serve_flow.gd::_pick_good` | 使用公共拿取动作 | 普通搬运仍直接指定 `carry_count=1` |
| `machine_progress.gd` / `serve_flow.gd` | 部分状态字段 | 三类生产时钟、投料、产出和工位释放分别实现 |
| `customer_movement.gd` | 路线、位姿与抵达 | 顾客业务状态仍从三种旧记录分别转换，`sync` 按模式分支 |
| 三个 action context | 执行同一种动作名称 | 预留、提交、返还和恢复的副作用各自实现 |
| `shop_view.gd` / `shop_play.gd` | 渲染节点和图片解析 | 旧库存状态读取与 `_serve_goods` 物品显示并不遵守同一展示协议 |

这些断层不等于每一处都已有可见故障，但它们使公共行为无法由一套契约保证。旧路线表中的“共享底座完成”不能继续代表本设计的完成状态。

## 3. 方案选择

| 方案 | 结果与代价 | 结论 |
|---|---|---|
| 继续为三种模式补适配器 | 改动较少；但取料、产出、派活和取消的副作用依然分散，新增店仍可能偏离 | 不采用 |
| 一个公共运行体系，模板组合公共能力 | 保留已验证的移动、动作、数值和场景模块，收敛权威状态及业务提交；需迁移旧状态并逐项证明一致性 | 推荐并作为本文设计 |
| 制作通用脚本语言或流程解释器 | 自由度高，但引入第二套编程环境、调试与存档问题，也不能天然保证基础行为一致 | 不采用 |

能力实现放在公共代码库；模板是受校验的数据，没有任意脚本回调。能力库只覆盖已有真实需求与已授权扩展示例，不预制无需求的系统。

## 4. 模板、能力、实例的边界

```text
店铺资源 / 空间模块 / 配方 / 岗位 / 能力配置
                    ↓ 校验与编译
        统一模板定义：设备 + 依赖 + 策略组合
                    ↓
        一个店铺运行实例、一份权威状态
        ├─ 库存与预留
        ├─ 生产与机器
        ├─ 顾客、订单与交付
        ├─ 派活与公共动作
        └─ 保存、事件与只读表现快照
                    ↓
        公共角色 / 机器UI / 场景显示
```

| 部分 | 可以定义 | 不可以定义 |
|---|---|---|
| 全局员工 | 属性、尺寸、动作资源、全局能力 | 店内复制的基础属性或专用控制器 |
| 空间模块 | 占地、权限、操作端口、显示端口、排序宿主、美术 | 自己计时、扣库存、驱动员工或结算 |
| 设备模板 | 公共能力及参数，如人工操作、自动批量、加料、封装 | 以机器名称编写独立加工循环 |
| 配方模板 | 输入输出、工序先后、并行、合流、端口引用 | 自行移动角色或直接改运行账本 |
| 岗位模板 | 区域、可执行能力、坐班范围、协作权限 | 另一套派活或移动实现 |
| 履约模板 | 接单、等候、自取/送达、附加品、支付与队列策略 | 独立顾客数组与结算循环 |
| 店铺实例 | 上述模板的引用、解锁、经营参数、资源绑定 | 专用玩法脚本、按店铺ID分支、任意回调 |

允许不同的是声明出来的业务条件和组合。相同条件下的操作必须走同一实现。公共能力也不能按店铺名分支。

## 5. 基础行为契约

### 5.1 库存、手持与显示

- 库存只有一个权威所有者。共享库存、订单专属物料、机器输入、机器输出、运输中和已交付物品是位置/归属的不同状态，不是不同经营模式的独立账本。
- 预留不等于领用：派活时只占用来源数量、目标容量和需要的工位，员工手上保持原状态。
- 员工必须到达取料端口，并完成拿取动作，才原子地把材料移入手持容器并显示手持图标。无限原料源也在此时生成对应数量，不能提前生成可见场景物品。
- 员工必须到达投料/交付端口，并完成放下动作，才把物品移出手持容器；手持显示从权威状态派生。
- 工位等待中的原料、中间品、成品默认只显示库存 UI。不能因物品属于某个订单，就自动在场景中生成图标。
- 奶茶原有货架展示、传送带运输、顾客用餐，以及煎饼台面加工等已有可接受展示，改为明确的公共展示能力与端口。`Buffer` 或工位坐标本身不自动授权展示库存。
- 加工展示是工序生命周期中的临时显示，不能兼任第二份库存。开始、完成、取消、读档的显示均由同一状态派生。
- 机器 UI、订单 UI、手持和场景展示从同一份只读快照读取，不从旧模式字典各自统计。仅隐藏第三店物品图片不算修复完成。

### 5.2 搬运与容量

- 公共搬运规划器读取员工有效搬运能力、来源可用量、目标剩余容量、归属兼容性与任务需求；普通搬运不能按模式写死一件。
- 数量取兼容候选需求与这些上限的最小值。订单专属物料仍保留逐份归属，不能为了合并搬运而混料或跨订单消费。
- 同一订单只需一份、单物品交付或单订单跟随时，实际只拿一份是业务需求的结果，不代表忽略员工容量。
- 多物品交付使用同一手持/容量/预留实现；不再另造一套普通搬运无法使用的容量逻辑。
- 路线、权限和无路处理继续复用现有公共运动能力。

### 5.3 加工、依赖与机器

- 人工操作、自动加工、批量加工、人工装料/卸料、中途搅拌、加料、封装均为公共能力。参数来自设备/配方和统一员工数值计算。
- 一份统一机器状态表达输入、加工中、可取输出、工位占用和进度。UI 不再猜某种模式使用哪个时钟。
- 工序只有在依赖、实物材料、工位和人员条件满足后才能开始；所有扣料、产出和工位释放经公共事务提交。
- 多路合流等待全部需要的输入；线性流程是相同依赖模型的简单配置。优先扩展现有 `consumes/produces` 编译能力，覆盖现有全部设备类型，而非另造菜谱语言。
- 自动与人工步骤的时长、员工是否被占用、是否需要领成品，由显式能力组合决定，不按旧模式隐含决定。

### 5.4 派活、连续工作与岗位

- 依赖图产生标准任务候选，公共调度器统一完成资格过滤、优先级计算、稳定排序、预留与领取。
- 跟随同一订单、继续当前工序、共享补货、坐班、区域协作、等待期间协助是具名公共策略。不同模板可以组合选择，不能复制整个派活器。
- 奶茶现有可接受的派活顺序与任务连续性是默认蓝本。煎饼的一人跟单通过订单归属策略表达，第三店的合流通过生产依赖表达。
- 最近未提交的 `transport_helpers/preposition_work/prefetch_inputs/continuation` 先纳入能力评审。不能将其现有的 serve 专属实现视为本设计已完成，也不能未经行为对照直接扩散到所有店。
- 所有动作复用公共执行器；预留、就绪检查、提交、取消使用公共操作实现。不能保留三个业务 context 各自复制相同的库存副作用。

### 5.5 顾客、履约与收款

- 一套顾客和订单记录承载排队、认领、等候、取餐、就座、用餐和离店；移动层只消费公共业务状态，不再从三种模式分别推导。
- 自取、柜台递餐、送桌、整单齐备、附加品先取后交付，作为公共履约策略组合。收款时机、价格取整和离队时机仍允许按模板声明，执行实现共用。
- 订单、人数、餐品销量和收入分别计数；付款、交付和事件广播必须保持一次性提交，读档和事件回调不能造成重复结算。
- 酸梅汤前台直售与其他前台产品使用相同的生产/取料/交付能力，不增加第三店专用快捷通路。
- 顾客生成、菜单抽样、耐心与流失采用公共策略及确定的随机数调用顺序。模板可以选择已有的固定/随机客流策略，不能复制顾客生成循环。

### 5.6 取消、暂停与恢复

- 每个任务持有公共预留记录。取消统一释放来源预留、目标容量和工位占用。
- 已取物品按公共取消策略退回来源并保留正确归属；已完成生产、已付款和已交付事实不回滚成未发生。取消补偿只能执行一次。
- 暂停时所有时钟停止；现有倍速只改变推进量，不改变前置条件、物品显示或动作顺序。
- 动作游标、剩余时长、物品归属、目标和预留可保存。读档从同一步续做，不重新拿料、重产或重复收款。

### 5.7 其他系统与制作入口

- 解锁、升级、招募、调岗、事件、引导和店铺推进继续走现有公共命令与数值机制；本轮核实其调用路径，已经共享的实现不重复重写。
- 新增事件或经营效果也通过公共能力及数据条件接入，不允许在场景节点、某家店UI或事件回调里直接改库存、订单或员工状态。
- 经营参数、文案和美术允许不同；UI只发公共命令、读取公共快照，不另算经营结果。具体美术接入仍遵守现有场景美术规范。
- 制作校验从声明的能力检查设备、配方、岗位、端口、展示和存档支持，不再让模式名替整组能力做隐式选择。错误同时给出配置路径、缺少的能力或端口，不能静默忽略无消费者的字段。

## 6. 扩展公共能力的准入

增加特殊行为必须一起交付：

1. 与店铺无关的能力名称、输入、输出、前置条件、占用与完成条件。
2. 公共实现和模板参数；拒绝未声明的参数与不支持的组合。
3. 缺料、无路、占用、暂停、取消、保存恢复和幂等语义。
4. 统一状态与表现快照的映射，不在某家店的画面脚本补状态。
5. 至少两个不同模板组合的复用证明，以及未启用能力的奶茶回归证明。

例如“取主餐→取例汤→一起交付”应组合公共取料与整单交付能力；两线合一应配置同一生产依赖系统。不能只把店铺专用脚本换成一个能力名称。

## 7. 旧实现与存档迁移

- `ShopRules` 保留外部命令入口；内部委派给统一运行体系。沿用现有 `ShopSession`、数值计算、角色定义、运动、场景模块和保存备份机制。
- 将旧定义转换成显式模板。转换器只在加载/编译边界使用，运行时不得依赖旧模式执行器。正式资源最终写出显式模板，而不是永远靠旧模式字段推测。
- 为统一运行状态定义独立版本；不能把新的库存/订单结构伪装成当前状态版本。外层存档信封是否升级由真实字段变化决定，不与内部运行版本混用。
- 三种旧状态分别转换成同一目标结构。保留稳定身份、升级、现金、收入、库存、归属、订单、预留、剩余时间、岗位和可恢复位置；保存前验证原字节备份。
- 当前业务格式的守恒验证与新格式验证同时参与迁移检查。转换失败保留原档、给出可操作错误；不换存档文件名、不清档、不默默重开店。
- 迁移开发期允许旧实现作为隔离对照；正式切换后删除可达的旧循环及重复业务副作用。历史夹具不进入游戏执行路径。
- 原始奶茶冻结文件维持原样。结构变化后比较规范化业务轨迹、动作时点、库存、结算和画面；不能重录基线来消除差异。

- 原有26个用户文件、用户提供的10张餐品图和5个奶茶冻结文件不属于本次重写目标，保持原内容。

- 不制作或修改美术；沿用已确认布局。制作源稿、诊断轨迹、对照报告和中间文件进入 `_work/`。
- 架构迁移先验证局内行为。最终完店时长沿用用户当前“先不管最终时间”的范围；旧完店门槛保留并单独报告，不能为让 CI 变绿删除门槛或改断言。

## 9. 迁移顺序与阶段出口

| 阶段 | 交付 | 阶段出口 |
|---|---|---|
| U01 基础契约 | 将奶茶可接受的拿取、手持、投料、库存UI、容量、任务连续性写成跨模板可执行验收 | 现有第三店差异被正确复现；旧错误展示测试不再定义产品要求 |
| U02 库存与动作 | 单一权威库存和公共预留/转移/取消；公共手持容器和容量规划 | 三类模板在相同条件下通过同一操作契约，不能靠适配器分别提交同名操作 |
| U03 机器与生产 | 覆盖现有设备的公共加工状态与依赖编译；线性、合流、自动、人工、批量能力 | 缺料、阻塞、取消与恢复守恒，机器UI数据完整 |
| U04 派活与履约 | 公共候选、调度、订单归属、岗位和顾客/交付/结算状态 | 一人跟单、前后厅协作、自取、送桌和附加品通过能力组合运行 |
| U05 公共表现 | 统一快照驱动角色、机器UI和明确启用的展示能力 | 三店拿取前无手持、完成才显示、投料后清除；库存不自动生成场景物品 |
| U06 迁移并切换 | 三种旧状态转换；正式三店与制作示例统一入口；移除可达旧循环 | 真实旧档启动/续做/重存通过；运行路径无三种模式分流 |
| U07 制作与门禁 | 更新店铺/员工模板、能力清单、示例、CI和验收报告 | 新示例只增配置与资源；公共能力可复用；完整验收通过且逐项有证据 |

阶段可分别验证，但 U07 之前不能称为“所有店已统一模板”。不得在中途把部分店走新体系、部分店走旧体系的状态作为最终交付。

## 10. 验收证据

| 验收类别 | 必须证明的事实 |
|---|---|
| 基础操作一致 | 同一能力在不同模板执行相同的预留、拿取、手持、投料、加工与取消状态变化 |
| 角色一致 | 同一员工的尺寸、基础数值、容量及升级跨店一致，实际任务使用这些数值 |
| 生产组合 | 线性、两支合流、共享批量源、前台直售、追加取物均只使用公共能力 |
| 顾客与结算 | 到位才操作；整单交付规则正确；付款、销量和订单完成没有重复或遗漏 |
| 表现一致 | 公共库存UI正确；无自动散落库存；手持/临时加工展示时点正确；明确展示端口排序正确 |
| 空间与时间 | 无路等待、权限、碰撞、暂停、1/2/4倍速以及拥堵下的规则与画面一致 |
| 存档兼容 | 三类旧档的拿取前/后、运输、投料、加工、交付、取消及读档恢复逐项通过 |
| 架构门禁 | 正式店入口都可追踪到同一运行体系与公共提交；旧业务 context 不能继续持有独立库存副作用 |
| 制作复用 | 一个新店与一个新员工只新增配置、资源与模块绑定；特殊能力在两种组合复用 |
| 奶茶蓝本 | 保留原冻结证据，明确对照业务轨迹、动作时点、状态和实际画面，不用新增测试数量替代 |

静态扫描只负责阻止明显绕过；实际运行轨迹负责证明路径被调用。二者都需要，不能只检查是否导入了公共脚本。

统一验收入口继续使用 `tests/shop_acceptance.json` 与 `tools/check_shops.py`；所有测试使用隔离 `APPDATA`，生命周期测试目录包含 `session-lifecycle-userdata`，不得读写真实玩家进度。规则、实际场景、窗口、Web导出与存档均需运行。已有未解决的完店门槛独立报告，不冒充此次行为验收通过。
