# 场景美术制作规则

更新：2026-11-10。适用项目：eatventure。本文依据已查阅的用户历史消息整理，不以旧助手的计划、提示词或总结代替用户要求。

当前任务只制作小炒饭馆场景，不制作人物、人物动作、UI 或经营功能。最终参考为本轮带灰瓦檐、木柱、灰砖墙脚、墨绿柜台及椅子、浅木桌、后厨淡花砖的版本。

## 1. 出图必须按批次同页组织

- 先清点唯一资产、核查资源库，再规划每张素材页包含哪些物件和需要几张图。
- 尽可能把一批相关物件放在同一张图中重绘，不采用一个物件单独生成一张图的默认流程。
- 同页生成的每件物品仍必须独立、完整、彼此留有空隙，方便拆分。
- “同页批量生成”和“引擎中独立复用”是两件事：生成页包含多件物品，导出后按唯一资产使用独立 PNG 或图集区域。
- 不为了减少页数把物件挤小、互相覆盖或裁掉边缘；批次数量在清单和分组方案中说明。

## 2. 统一正交投影

- 保持参考所用的统一正面俯视角。用户曾明确要求“俯视45度视角下，正交视图”。
- 无透视汇聚、无消失点、无近大远小；平行结构边保持平行。
- 不以等距斜摆、透视倾斜或整件旋转的效果代替已确认的正交视图。
- 同一批物品和不同批次的镜头角度必须一致；新资产放回场景后也要重新核对。
- 确需正面、侧面或背面时，保持物件设计与比例一致，只增加实际需要的视图。

## 3. 唯一资产复用，已有资源优先

- 相同物件只制作一个资产，多处通过实例、图集引用或位置变换复用。
- 左右镜像相同的物件共用一份资产；不能因为摆放位置不同就重新生成一套。
- 优先检查现有资源库。造型、角度和风格适合的资产直接复用，需要改色或新造型的再列入制作清单。
- 仅当结构或所需可见面确实不同、镜像不能得到正确结果时，才制作必要变体。
- 本次八张相同圆桌只需一个桌子资产；相同椅子、同款碗盘、重复锅具与装饰同样按唯一资产计算。

## 4. 按实际使用拆分，固定组合保持完整

- **不为拆而拆。** 先判断游戏里是否真的需要独立移动、摆放、复用或切换状态，再决定是否拆开；不能只因为看得到不同零件就全部拆散，也不为尚未确定的未来功能预先细拆。
- 固定组合保持一个完整素材。用户曾圈出装袋机里的煎饼、竹筐里的食物并说“这种可以不用拆”；对应交付将装袋机与机内包装、竹筐与食物保留为完整图素。
- 装满食材的固定料架不默认拆成空架和每颗蔬菜；一碗饭、一笼包子等不默认拆成空容器和逐颗内容物。确需空/满或不同餐品状态时，优先提供完整状态图；只有实际功能需要才单独拆内容层。
- 桌面上需要独立使用的完整物件与桌子分开。例如饭碗作为一件与桌子分开，不等于饭碗还必须拆成空碗和米饭；可搬运餐品、工具和设备仍按完整使用单元处理。
- 通用工作台与其加工物料分开。例如旧需求明确指出：手打台是通用的，柠檬是单独图素。这不要求把固定料筐里的每颗物料都逐一拆出。
- 物件必须是完整轮廓，补齐原画中被人物或其他物件遮住的部分。
- 不按原画每一次出现重复切一份；先建立“出现位置 → 唯一资产”的对应关系。
- 固定的一体建筑和无功能陈设可按完整环境模块制作；只在实际遮挡或编辑需要处保留层，不默认拆到每根柱段、每块砖。
- 制作前逐项写清“为何要独立”；没有具体使用理由的内容合并回完整物件。唯一资产去重与拆分粒度分别核对，资产数量多不代表完成度高。

## 5. 忠实还原已经确认的原画

- 同时核对布局、造型、大小比例、颜色和描边粗细，不只核对物件名称。
- 不擅自提高亮度、把木色改橘红、把设备画窄、改变柜台结构或挪动已确认的位置。
- 环境要完整，包括地板、墙面、植物、座具、建筑边框等，不只制作主要设备。
- 用户调整过的大小与位置以其最新确认稿为准，不拿早期生成稿覆盖。
- 画面要精致、清晰，放回实际显示尺寸后仍能辨认结构。
- 历史案例中的某一套配色、某张 L 型桌或某种凳子，仅适用于其对应场景。本次餐馆仍以当前最终原画为准。

## 6. 人物、文字和独立阴影不烘入运行素材

- 本次只制作场景，不生成、拆出或重绘员工、顾客和角色动作。
- 历史预览稿中的全部人物、文字和独立接触阴影属于预览层，不作为贴图烘入游戏。
- 运行时文字和投影/接触阴影由引擎代码绘制；需要保留的字牌、标识，其文字与底板分开处理。
- 物体自身的明暗体积仍应保留；“阴影不烘入”指独立落地/接触阴影，不是把物件画成没有明暗的平面色块。
- 功能状态相关的物品、火焰和蒸汽不要固定画在空家具或空设备上。

## 7. 尺寸与导出

- 替换已有游戏图片时，最终画布像素宽高保持原资源尺寸，不因重绘而改动。
- 等比例缩放并保留必要透明留白，不拉伸物件来塞满画布；核对有效内容大小和底部对齐，避免图素看起来忽大忽小。
- 新增资产单独规划适合实际显示的尺寸，再导出压缩；不把某一次“512即可”推广为所有资产的固定尺寸。
- 项目既有交付方式为透明 PNG/图集。透明区域应为真实 alpha，不带白底、棋盘格或生成页底色。
- 拆图和导出后检查完整边缘、裁切、清晰度与透明边缘。

## 8. 固定环境与功能资产分组

- 基础设施和与玩法功能无关的固定环境，开局就存在。
- 需要购买、解锁或随状态变化的功能设备、桌椅和物品保留独立分组。
- 固定环境不等于把整间店和所有功能物件合成一张背景；仍要保留复用与必要的遮挡关系。
- 单纯美术制作不顺带修改游戏经营流程、数值或 UI。

## 9. 先整理预览，确认后接入 Godot

- 流程：核查旧资产 → 唯一资产清单 → 同页批次规划 → 正交重绘 → 拆图导出 → FigCraft 图层与布局预览 → 用户确认 → Godot 场景接入。
- 保留可编辑的场景层次，优先继续编辑当前确认的源稿，不无故另起一份不对齐的布局。
- 用户确认整体原画，不等于已经验收后来重绘的分层资产和组合布局。
- Godot 接入时复查实际渲染：位置、比例、裁切、遮挡、透明边缘与显示范围，不能仅凭生成图判断完成。
- 2026-11-10 已开始小炒饭馆拆图。首轮 57 图素方案经用户指出“拆的太碎了”，属于粒度不合格的过程稿；后续按本节完整组合规则修订，尚未接入运行场景。

## 10. 源文件和运行资源分离

- 参考图、生成原图、FigCraft/PSD 源稿、工作工具、中间切图和验收图集中放在本地制作工作区。
- 沿用项目 `_work/<主题>/` 的现有做法；该目录不进入 Git，也不由 Godot 导入。
- 游戏只引用正式运行资源；提交以游戏运行资源、必要场景/代码和相关项目文档为范围，不夹带源稿和制作中间产物。
- 不依赖系统 Temp 长期保管最终参考；已将当前批准图复制到 `_work/stirfry/references/user_uploads/stirfry-approved-concept-2026-11-10.png`。
- 不把本地制作工作区里已有的旧场景规则、路径和资源名称直接当成当前项目接口。

## 制作前/交付前核对

- [ ] 已确认本次范围与最新参考，未混入人物或 UI 制作。
- [ ] 已清点旧库可复用资产；同物件和镜像物件没有重复生成。
- [ ] 已列出同页批次与每页唯一物件，且不采用一物件一页。
- [ ] 正交投影、统一俯视角、比例、颜色、描边与原画一致。
- [ ] 固定组合保持完整；每个独立图素都有具体使用理由，没有默认拆出空容器、逐颗食材或建筑零件。
- [ ] 桌面完整物件与桌子按独立使用需要分开，完整且无互相遮挡的缺口。
- [ ] 地面、建筑和装饰齐全，功能资产与固定环境有清晰分组。
- [ ] 无烘入的人物、预览文字和独立接触阴影；透明边缘干净。
- [ ] 旧资源替换尺寸一致；新资源尺寸有规划；无拉伸和裁切。
- [ ] FigCraft 组合效果已由用户确认，才进入 Godot 接入阶段。
- [ ] 源稿、工作工具和中间图留在本地工作区，提交范围仅包含游戏所需文件。
