# 公共店铺能力核心（迁移中）

本目录属于 `2026-11-12-unified-shop-template-design.md` 的实施。正式三店尚未切换；不能将这些模块的测试通过等同于正式店行为已经统一。

## 唯一所有权

| 模块 | 所有权 |
|---|---|
| `inventory.gd` | 物品lot、预留claim、归属与守恒；库存汇总由查询派生 |
| `bundle_transfers.gd` | 引用普通搬运claim，原子预留/交付/返还整组；不保存第二份数量 |
| `machines.gd` | 机器阶段和时钟；加工扣料与产出委托库存事务 |
| `capability_runner.gd` / `action_context.gd` | 员工请求、动作程序和调用公共移动；不持有第二份库存 |
| `compiler.gd` | 严格编译配置，生成无脚本回调的定义 |
| `recipe_normalizer.gd` | 只在制作边界转换已支持的正式生产定义；缺规则时返回路径和错误，不运行旧循环、不转换玩家状态 |
| `content_projection.gd` | 模板内容指纹投影；明确区分工时/分数与数量、依赖、端口、阶段等结构事实 |
| `runtime.gd` | 生产份数、依赖完成事实、公共生产/服务推进入口及恢复 |
| `restock.gd` | 共享补货的批次引用和请求；不独立搬运或修改库存 |
| `batch_recipe.gd` | 将每份配比按显式产量修正计算整批请求；在制数量仍只保存于库存operation claim |
| `numeric_limits.gd` | 从公共修正器派生容量/槽位目标；实际占用仍由库存claim和机器批次持有 |
| `source_demand.gd` | 从生产图、单位完成事实及真实库存/claim派生需求，不保存第二份需求账本 |
| `orders.gd` | 排队、订单明细、生产绑定、交付凭据、付款、座位租约、用餐和离店事实；钱与销量仍使用公共RuleSales |
| `customers.gd` | 顾客位置、路径和真实抵达；不含三种经营模式的分支 |
| `service.gd` / `service_policy.gd` | 编译并组合接单、生产请求、备餐、携带、送达、座位、用餐和真实离店；只保存履约引用和顾客动作时钟 |
| `arrivals.gd` | 固定/随机到店时钟、开张一波顾客、加权菜单请求；不保存第二份随机数状态 |
| `customization.gd` | 可选到店选项抽样、显式配方变体和原价倍率；不执行封装动作、不保存第二份库存或RNG |
| `dispatch.gd` | 统一角色/岗位权限；普通搬运、整组搬运、加工与接单均在领取、推进及恢复时检查 |
| `dispatch_leases.gd` | 员工跟随归属和机器阶段租约；只保存身份引用，不复制物品或加工时钟 |
| `view_frame.gd` | 从权威状态生成只读UI/手持/显式展示数据 |
| `processing_display.gd` | 校验台面输入/端口并投影真实加工claim；与货架展示共享同一份物品数量 |

当前生产运行器的owner提供名册、导航、共享属性与修正器接口。受控测试使用既有ShopRules提供这些接口，新核心不读取它的旧库存/serve业务账本。正式切换时要移除旧账本与执行路径，不能长期并行保存两份权威状态。

## 库存契约

```text
reserve → 原库存保持，来源和目标被预留，手持为空
pickup  → 到位动作完成后进入手持，来源空间保留用于取消返还
drop    → 到位动作完成后进入目标，手持与返还空间释放
cancel  → 释放预留；已拿实物回到原位置/归属；无限源领用销账
```

- `reserve_transfer(worker,...)`与`reserve_actor_transfer("customer:<id>",...)`使用同一个实现。员工ID与顾客ID有不同命名空间。
- `hand:<staff id>`、`hand@customer:<id>`是受管理容器，不能通过seed、普通搬运或加工伪造/转移手持。
- 已拿材料继续由原claim占用，不能同时交给另一个任务加工。
- `reserve_operation/complete_operation`原子处理多输入配方。设备内建无限原料也走同一事务，既不生成散落物品，也不虚构员工取料。
- 所有视图默认不画等待库存。`stock_showcase`必须声明展示端口；顾客手持使用同一携带者投影。
- `reserve_bundle(actor,entries,capacity)`整组精确预留；缺一件或容量不足不留半份预留。员工逐站`pickup_bundle_part`，顾客同点`pickup_bundle`；全部拿齐才可整组`drop_bundle`。子claim不能绕过整组生命周期；中途取消一次性归还已取物并释放未取物。
- `CapabilityRunner.transfer_bundle`通过真实RuleActions逐站取货再统一交付；每站可声明`pickup_seconds`，员工手速统一应用。`interact(...,"admit",guest)`通过公共移动/操作计时产生一次完成或取消结果，不接收店铺脚本回调。

## 模板结构

`SpecShopTemplate`声明`places/machines/recipes/restocks/service/dispatch/hop_seconds`。配方的source/process/transfer节点以显式生产者绑定输入；同一编译器处理线性和合流。机器profile声明人工加工、装卸、搅拌和槽位，不提供任意回调。未知能力、无效数量、缺端口、循环和产量不足都会报错。

规则时长复用`RuleNumbers.capability_seconds`：机器修正与工序fixed数据决定基础工时，员工实际手速由人工阶段应用。自动锅和人工机器不能各自另算升级效果。

source节点可声明`timing_target`和`fixed`。指定目标后，取料使用同一公共数值公式；`fixed`跳过机器速度/时长效果，保留目标调平倍率，员工手速由真实拿取动作应用一次。未指定目标的既有模板保持字面工时。生产取料、最终出品描述和服务备餐/送餐共用该计算，不能各自另算。

### 正式配方转换与内容身份

`recipe_normalizer.gd.from_shop(shop, selection=[])`返回`scope=production_only`、`template`和`errors`。它不读店名，不修改正式Resource，不选择旧执行器；有错误时不返回可运行的半份模板。空配方/工位/库存、缺操作端口、参数类型错误均在制作边界报错。

当前可转换小炒饭馆7道显式配方，以及奶茶店`lemonade/lemon_tea`、煎饼摊`soy`的生产子集。实际测试使用原导航、原员工和公共运行器，并在正式交付坐标声明测试收货容器，完成真实取货与放下；它不表示正式服务已经接入。转换结果尚不包含阶段解锁、选项、最终出餐口暂存配置、岗位和旧档转换，不能直接挂到正式入口。

动态备货、设备内建输入的正式绑定、自动工作台批次/时钟、连续工作、台面加工展示、隐式携带变换和空产出的收尾交接尚有能力映射缺口。转换器拒绝这些情况，不能丢步骤或用人工工时替换自动机器时钟。

`ShopContentContract.describe_template(template)`生成独立的玩法和结构SHA256。配方数量/依赖、端口、容量、初始库存、槽位和归属策略是结构；明确列出的工时、分数和客流权重允许数值调平。人工装卸从0变成正数会新增阶段，属于结构变化。仅步骤文案从指纹中排除；名为`seconds`的物品仍保留数量。此接口尚未把模板字段接入正式`SpecShop`或玩家存档，也未实现内容版本采用。

### 公共备货策略

`restocks.<id>`省略`policy`时保持原有整批填库存行为。可显式配置：

```gdscript
"policy": {"mode":"demand", "base":3, "per_waiting":1, "low":0}
```

目标为`min(stock_limit,max(base,未覆盖需求数量×per_waiting))`；实际库存加在制产出低于目标或低水位时才准备整批生产。整批容量、物料、装卸和搅拌仍由公共库存/机器能力控制；目标可以被一整批略微超过，但不能超过库存硬上限，也不能拆批或丢弃超量产出。低水位是触发条件，不表示要填满容器；倍率0明确禁用该项需求增量。默认fill模板不计算额外需求。

`Runtime.source_demand()`是只读投影：输入容器已有材料、已预留/在途搬运和已经开始的加工不会再计缺量；来源型最终出品的有效领取凭据持续覆盖它的生产份数，顾客吃完也不会重新触发旧单。取消领取会重新打开需求，同时由原库存事务归还实物。需求策略首批只接受一种库存产物，且整批不能超过配置的库存上限，避免混合批次掩盖单项缺料或空仓时越界启动；未知字段和策略报错，不能挂店铺回调。

柜台递餐/送桌的候选同时检查该份出品是否已经在顾客容器或被另一员工预留配送，避免共享库存还有余量时，两名员工重复配送同一份生产绑定。不同份数仍可由不同员工协作。

此能力尚未自动采用旧奶茶店stock中的`base/per_waiting`：核查发现旧handoff循环实际按输入容量、整批启动和工单推进，没有消费这两个字段。正式迁移必须按真实行为显式配置并对照轨迹，不能按注释直接替换。

### 每份配比与每锅份数

共享补货可声明可选批量绑定：

```gdscript
"consumes": {"leaf":1}, "produces": {"tea":1}, "sources": {"leaf":"pantry"},
"batch": {"target":"pot", "base":3, "max":8},
"fetch_seconds":0.6, "fetch_timing_target":"pantry", "fetch_fixed":false
```

声明batch后，consumes/produces是每份配比。公共`batch`修正器在开锅前计算整批投入与产出，员工按真实容量分次搬齐材料后才开锅；每锅工时仍由seconds及公共工时公式决定。max必须同时满足已声明输入/输出容器、库存上限与整数表示范围，不能靠溢出或截断取整。没有batch绑定时，原数量和编译签名保持原样。

开锅后以原库存operation claim中的配比为准，途中升级不改旧锅数量；下一锅才应用新份数。恢复校验实际配比是合法的整批整数倍且在声明范围内，不要求旧锅数量等于当前升级值，也不另存数量账本。fetch_timing_target/fetch_fixed使补货取料复用公共工时和员工手速；fixed=true必须声明目标，不能静默忽略。

奶茶共享锅组合测试使用原导航、员工、30秒煮茶、两次搅拌和人工装卸。原开局batch基础效果为2，覆盖缺省基数3；测试先做2份、取走1份，再用显式修正做6份，原料总消耗8份。卸料工时按旧handoff真实使用的hop_seconds显式声明。这仅验证共享锅子流程，尚不包括原料箱采购/解锁、旧派活顺序、完整配方和正式服务入口；运行时扩容/槽位升级须另行声明下方的数值绑定。

### 明确声明设备内建供料

设备输入容器先声明已安装的供料，例如`places.mix_in.infinite=["milk"]`；配方再明确绑定：

```gdscript
"consumes": {"tea":1, "milk":1},
"inputs": {"tea":"tea_source", "milk":{"capability":"integrated"}}
```

只有严格的integrated绑定和该机器输入容器的安装声明同时存在才有效。缺绑定不会自动推断；供料未安装、未知键和回调均编译失败。茶仍从生产者实际搬到机器，牛奶不增加虚构来源节点、员工拿取任务或手持图标；生成与消耗在已有库存operation完成时一次性记账，取消和恢复共用原事务。

内建输入不计入物料搬运需求或生产者依赖。相同库存能力也支持共享补货中的内建配料，并随batch份数缩放；不新增数量表。普通来源绑定和未启用能力的模板保持原编译结果。

`tests/fixtures/template_tea_production.gd`是制作期生产子流程：原导航/名册、2份共享煮茶、实际搬茶、内建牛奶与4秒自动调制。它假定材料已安装，不负责采购/解锁、正式出餐口、封口、岗位和完整店铺接入。

### 容器容量与机器并行槽位

容量和槽位可独立声明公共数值绑定：

```gdscript
places.shelf = {"port":Vector2(100,100), "capacity":4,
    "capacity_binding":{"target":"shelf_upgrade", "max":8}}
machines.mixer = {"input":"mix_in", "output":"shelf", "profile":{"slots":1},
    "slots_binding":{"target":"mixer_upgrade", "max":3}}
```

基础值来自capacity/profile.slots，分别读取外层公共capacity/process_slots修正。目标必须是声明max以内的有限整数；容量允许0，槽位至少1，不截断小数。绑定缺省或为空不增加编译字段和签名；无上限容器不能声明容量绑定。补货整批范围按声明max校验，运行时仍须满足实际可用容量，不因预留了未来升级范围而提前扩容。

扩容允许真实新增库存/并行加工；缩容保留实物、输入/输出预留、手持物的返还空间及在制批次。有效上限为max(新目标,实际占用)，占用超过目标期间阻止新增占用，原工作照常完成；普通及整组交付、取消和加工完成后立即收敛，不等待下一帧。输入/输出共用容器时仍只有一份容量。

目标缓存是派生策略，库存和机器快照仍使用version=1，不增加数量账本。恢复仅放宽已声明绑定的容量/槽位数值，并检查范围；端口、无限供料、其他profile和未绑定定义仍严格匹配，全部验证通过后才采用演员。外层负责恢复修正器，再恢复运行器。暂停不应用新目标；非法目标在推进时间或部分扩容前返回错误。

`Runtime.frame().limits.capacity/slots[id]`暴露target/applied/used用于诊断，不保存第二份占用。此能力尚未映射正式三店升级；旧正式入口的校验器明确拒绝capacity效果，防止制作数据被静默忽略。

### 配方中的实物交接

已有成品搬到另一容器，用transfer节点表达，不用一次消耗/重产的加工假装搬运：

```gdscript
{"id":"to_pass", "capability":"transfer", "input":"mix",
    "place":"pass", "item":"milk_tea", "count":1, "seconds":0.6}
```

input是已有生产者节点，place是目标容器；物品、数量和归属随真实搬运保持，不改变created/consumed账本。编译器校验生产者、物品、数量、容量声明和依赖，禁止同容器搬运、无限供料目标、未知字段和回调。count缺省为1，多件请求作为整组精确领取，物料/目标容量/员工容量不足时整组等待，不提交半份终端交接。

领取候选复用公共整组搬运、派活权限、路径和动作。拿取工时来自生产者，seconds是目标放下工时；可选timing_target/fixed复用公共数值公式，员工手速仍只应用一次。未声明目标时使用字面工时；fixed=true必须有目标。预留不显示手持，真实拿取后才显示，放下后清除；等待库存默认只有UI统计。

unit.running只引用原bundle ID，真实drop凭据决定节点完成；取消归还实物并允许重新领取。恢复检查唯一bundle、源/目标、物品/数量、原归属/新归属、依赖和完成事实，再采用演员。快照仍使用既有version=1结构。机器与bundle编号各按节点能力解释，不能拿一个交付凭据完成两道工序。

transfer可位于配方末尾，也可继续输入普通process完成封装等明确变换。需求投影区分内部图搬运和最终顾客领取，已完成交接不会因食物被后续消耗而重新备货。柜台、自取、送桌继续读取相同的最终出品描述，无新增服务执行器；未声明transfer的模板编译结果和签名保持。

此能力不自动转换旧配方中空produces，也不代表封口/装袋选项已迁移。旧pickup还包含堂食/外带分区、封口时钟和容量；旧装袋还有抽样、价格和隐式换物/台面展示，均须后续显式映射。奶茶验证只在已安装原料的生产子模板后接一段到原seal坐标的实物搬运，不是正式三店入口切换。

### 台面加工展示

机器可选声明加工中原料的展示；省略或空字典时保留原编译结果、签名和机器快照形状：

```gdscript
machines.roll.processing_display = {
    "capability":"processing_item", "items":["pancake","crisp_pancake"],
    "points":[Vector2(400,300)], "host":"roll_table"
}
```

items列出允许展示的有限投入物，每次加工最多匹配一个；points明确每个并行槽位的显示坐标，必须覆盖profile.slots和slots_binding.max；host是显式排序宿主。原料未被声明配方/补货使用、物品重复、无限供料、同一加工匹配多种输入、缺端口和未知键/回调都在制作时拒绝。其他配方未匹配items时仍用普通库存UI，不显示附近另一份等待原料。

输入实际放入容器并被加工operation预留后，从claim.parts取得显示物品及数量。等待员工操作、自动加工、搅拌、卸料期间保留同一真实输入，完成/取消立即移除；未开始加工的等待库存与已完成产品默认只在UI记录。手持量仍来自原库存：运输时画手持，到位放下后清除，再显示对应加工输入。展示不推进机器、不消费/生成物品，也不保存进度或可见物品列表。

启用能力后，机器定义保存静态slot_ceiling，运行批次保存slot整数引用。新批次领取空闲编号，完成/取消释放，仍在制的批次保持原编号；槽位升级、缩回、暂停、召回和恢复都不会重排。并发数量仍使用原process_slots和真实占用，端口编号范围独立于并发数量：缩至1时仍可保留原slot=1的批次，新工作按新数量等待或领取空闲低编号。

加工展示与stock_showcase同时启用时，投影从货架绘制中排除已经画到台面的那部分lot数量，不重复画同一份原料；库存UI始终记录完整权威数量。Runtime.frame()自动合并已编译的绑定与额外展示参数，冲突返回error并清空draws，不回退到操作坐标。加工draw包含machine/run/slot/item/count/pos/host；字段全部派生，修改返回帧不改规则状态。

恢复严格校验slot形状、静态范围、活动批次占位唯一性及原库存/机器事务，再采用演员。旧未启用机器仍没有slot_ceiling/slot字段，私有快照继续使用version=1。此批提供公共投影，正式场景消费这些draw和旧put_down工序的配方/端口转换仍待接入；旧卷饼/装袋显示路径尚未替换。

## 公共服务配置（受控模板已接通）

`service`为空的模板只运行生产；声明后由同一个`Runtime.step`组合整个服务周期：

```gdscript
service = {
    "menu": {"dish_id": "recipe_id"},
    "admission": "employee", "admission_port": "front", "admission_seconds": 0.6,
    "admission_roles": ["staff"],
    "delivery": "self_pickup", "pickup": "pass", "customer_capacity": 2,
    "delivery_roles": ["staff"],
    "seats": {"seat:dine/0": "table_staff_port"}, "eat_seconds": 3.0,
    "orders": {"pay_at": "on_deliver", "queue_release": "after_take"}
}
```

- 菜单引用现有菜品价格接口和模板配方；报价在真正接单时获取。当前服务配方每份最终出品数量必须为1；机器内部仍可批量加工。不能静默把多件出品算成一件销售。
- `automatic/employee`只决定是否由员工在接单端口完成工时。顾客必须实际抵达队首，取消员工接单不能创建订单或收费。
- `counter`声明`handoff_port`，顾客到达`pickup`后员工可分批交付；最后一份交付后按订单策略结算。`table`使用具名座位和员工桌边端口，必须等顾客真正就座。
- `self_pickup`由员工备齐取餐点库存，顾客实际到位并完成取货工时后整单拿起，携带到具名座位/出口再放下。顾客携餐时不再为同一订单重复备货；取餐点已有的成品可以直接使用，无需虚构员工搬运。
- 座位目前从接单持有至顾客真正离店，满座会保留顾客在队列等候。用餐结束逐生产份数通过公共加工事务消耗食物，保留可恢复的消耗凭据。
- 员工资格与实际移动使用同一`access_profile`；未配置角色名单时可由所有部署员工承担相应服务任务。生产、补货、接单和交付现由同一候选池排序，跟单和机器阶段持有按下方公共策略配置。
- `Runtime.arrive([{dish,qty},...])`仍可显式输入顾客；自动客流须另行声明下方能力。正式升级门槛仍需在正式入口切换时组合。

## 客流与岗位配置

### 订单选项与配方变体

`service.customization`可选；省略或空字典时，原定义、签名和请求/订单形状保持。启用后声明选项及每个组合对应的普通配方：

```gdscript
service.customization = {
    "options":[{"id":"bag", "unlock":"bag_station", "share":0.4, "price_mult":1.25}],
    "variants":{"dish_id":[{"options":["bag"], "recipe":"bagged_recipe"}]}
}
```

请求第一行是主菜，其余行为附加品；选项只作用于第一行，qty>1时每份都使用该变体和单价。某菜品有变体才参与对应选项抽样。unlock引用外层已声明工位，开放查询复用公共station_unlocked；未知工位在运行实例创建时拒绝。首批最多8种选项，每道菜必须为所有适用选项的非空子集声明一个明确配方；未知、重复、遗漏组合和未用选项均报错，不在运行中猜测如何拼接工序。

`Runtime.arrive(request)`在到店时按声明顺序抽样，复用外层唯一RNG。满队、选项不适用或工位未开不抽选项随机数；已开放且适用的概率0/1选项仍抽一次，保持旧语义。`Runtime.arrive(request,["bag"])`明确指定选项，`[]`明确不选，均不抽样；非法/重复/未开放选项在统计到店或流失前被拒绝。自动客流先抽菜单，再走相同选项路径，不额外保存RNG。

选中的ID按声明顺序保存在第一行request/line的可选options数组；未选也保存空数组。接单和恢复不重抽、不因工位随后关闭而清空历史选择。恢复交叉检查已声明组合、配方、最终物品和订单行；篡改、缺失或非规范顺序在采用演员前拒绝。没有此能力的历史模板不接受无来源的options字段。

首批显式要求`service.orders.rounding="order_round"`：接单时通过公共RuleNumbers.raw_price查询主菜原价，再按已选倍率相乘；附加品仍用各自原价，最终通过共享结算整单取整。报价按行索引传给Orders，避免同一道菜同时作为主菜和附加品时覆盖不同价格。报价、实际物品和销量身份分开：变体可产出packed_item，销售仍计原dish；不会为包装另计一份销量。选项概率/倍率是内容数值项，配方、组合和解锁绑定仍是结构项。

变体是原process/transfer依赖图，柜台、自取、送桌共用相同生产与履约；新模块不解释SpecStep、不生成回调或另一套封口/装袋循环。此能力不等于已转换正式奶茶封口和煎饼装袋：台面加工展示、隐式携带变换、正式门槛/配方/旧档和三店入口仍须接入。

自动客流是`service.arrivals`的可选能力，默认不创建时钟、不消耗随机数。示例：

```gdscript
"arrivals": {
    "pattern": "exponential", "interval": 8.0, "first_delay": 2.0, "opening": 1,
    "choices": [
        {"weight": 3.0, "request": [{"dish": "dish_id", "qty": 1}]},
        {"weight": 1.0, "request": [{"dish": "dish_id", "qty": 1}, {"dish": "side_id", "qty": 1}]}
    ]
}
```

由`Runtime.set_service_open(true)`开放，首次开放只生成一次`opening`波次；关闭暂停到店时钟，重开保留剩余等待。间隔使用公共`RuleNumbers.flow_interval`应用客流倍率和调节值，固定间隔本身不抽随机数；指数间隔与菜单抽样复用`RuleSampling`，旧实现也调用同一公式且奶茶冻结轨迹不变。满队只记录流失，不抽一个随后丢弃的菜单。自动顾客仍走相同的订单、生产和履约能力。

随机数由外层唯一`owner.rng`持有，客流快照只保存开关、剩余时间和尝试次数。完整会话保存必须同时由外层保存RNG一次；不能只恢复客流计时器就承诺相同后续订单。当前抽样在到店时完成；正式迁移还须声明旧送桌店在接单时抽菜单的时机、阶段菜单权重/爬坡与传单波次，不能丢掉这些规则。

`dispatch`允许声明`roles`（移动权限profile）和`posts`（岗位ID）。两者都为空时保留原公共运行器的可执行范围；声明某角色或岗位后，未列出的能力默认禁止。岗位定义覆盖角色；一旦声明岗位表，未列出的非空岗位不获得其他角色的权限。

```gdscript
dispatch = {
    "roles": {"staff": {"operate": ["*"], "transfer_from": ["*"], "transfer_to": ["*"], "interact": ["front"]}},
    "posts": {"device_post": {"operate": ["device_id"]}}
}
```

`operate`引用设备，`transfer_from/transfer_to/interact`引用声明的端口，`*`为明确授权全部。整组搬运必须同时具有每个取货端口和交付端口的权限；不能由某个子项绕开。实际执行器在创建库存claim前检查，直接调用也不能绕开；推进前重新核对岗位和移动profile，失效时统一取消/归还/释放机器，且不再推进已移走员工的人工时钟。恢复也检查当前外层岗位。

## 公共派活与租约

生产、补货、接单、备餐和员工交付只产生标准能力候选，唯一员工分配循环调用同一个`Dispatch.rank`再领取。服务组件不再另外遍历员工分配任务。`Runtime.candidates_for(worker)`返回脱离权威状态的候选，可用于诊断，不预留物品、不推进时钟、不抽随机数。

```gdscript
dispatch = {
    "affinity": "exclusive", "affinity_bonus": 100.0,
    "continuation_bonus": 20.0, "travel_penalty": 0.01,
    "hold_machine": true, "help_while_waiting": true,
    "scores": {"admit": 400.0, "deliver": 300.0, "stage": 250.0,
        "operate": 200.0, "transfer": 100.0,
        "restock_operate": 200.0, "restock_transfer": 100.0}
}
```

- 同分保留原候选顺序；实际已完成工序触发`continuation_bonus`，真实导航路径长度按`motion_units`归一后应用路程扣分。无路的候选不抢占员工，直接请求仍由公共移动保持阻塞，不回退直线穿越。
- `affinity=none`为默认；`prefer`优先继续本人的同单工作但允许其他员工协助；`exclusive`让一名员工从接单、主餐/配餐生产跟到交付。接单租约从`guest:<id>`晋升为`order:<id>`；没有顾客绑定的手动生产请求以`unit:<id>`跟随至生产完成。跨职责合作的店铺应选择与权限配置相容的策略，不能把exclusive当成任意分工下的加速选项。
- 跟随归属从真实claim分片、原所有者和分配所有者推导；省略owner或改用整组搬运不能绕过。exclusive不允许混合不同订单的整组，失败时整份候选库存不采用，不留半份预留。共享无归属杂活可在允许协助时执行，原跟单租约仍保持。
- `hold_machine=true`保留同一机器运行批次的装料、自动等待、搅拌、卸料阶段给原员工；其他员工不能抢走后续阶段。`help_while_waiting`决定其等待期间能否协助；已持有机器需要人工阶段时优先返回。一个员工持有多锅时，可以继续任意一锅，不能互相卡死。
- 订单交付、独立生产完成或机器批次结束自动释放相应租约；召回、调岗、区域变化或取消也释放，保留已发生的库存/收入事实与机器剩余工时。持有期间空闲的员工也要释放租约，不依赖是否正有动作程序。
- 快照保存跟随/机器租约和任务scope；恢复先交叉校验真实物品归属、订单绑定、机器运行和当前外层员工身份，再采用演员。未知/重复租约、伪造scope、丢失活动操作员租约均拒绝；已完成来源的后续搬运不会生成过期租约。

这里的机器持有范围是同一运行批次，尚不代表跨批次物理工位排他、动态坐班专属段、完整前后厅协助和兼容生产搬运合并都已完成。正式奶茶派活顺序仍须通过真实配方转换后的冻结轨迹/画面对照验收。

## 保存边界

快照包含无对象引用的状态；恢复先验证全部候选再采用。生产图、机器、库存、员工动作、路径、权限、补货引用和交付凭据各有交叉校验。

服务快照同时交叉校验生产份数绑定、接单员工租约、履约整组、顾客手持、目标与座位、用餐消耗凭据和动态顾客容器。接单、生产、员工取货、顾客携带、用餐五个阶段的恢复与连续运行对照一致。失败采用不修改原员工或服务。

这是开发期的新内部格式，尚未写入正式玩家存档。正式ShopSave仍需旧三种模式的转换、原字节备份、全局财务/名册整合和内容采用。公共钱包仍只由外层持有一次，服务快照不复制钱包；测试明确独立恢复外层财务后再恢复服务，不能将其当成已完成玩家存档迁移。
