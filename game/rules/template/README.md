# 公共店铺能力核心（迁移中）

本目录属于 `2026-11-12-unified-shop-template-design.md` 的实施。正式三店现由 SpecShop.runtime_template 接入同一个 Runtime，外层 ShopRules 只持有命令、购买、钱包和随机状态。U06 的迁移与正式入口说明见本文末；此前章节保留各批实施时的历史边界。

## 唯一所有权

| 模块 | 所有权 |
|---|---|
| `inventory.gd` | 物品lot、预留claim、归属与守恒；库存汇总由查询派生 |
| `bundle_transfers.gd` | 引用普通搬运claim，原子预留/交付/返还整组；不保存第二份数量 |
| `machines.gd` | 机器阶段和时钟；加工扣料与产出委托库存事务 |
| `capability_runner.gd` / `action_context.gd` | 员工请求、动作程序和调用公共移动；不持有第二份库存 |
| `compiler.gd` | 严格编译配置，生成无脚本回调的定义 |
| `recipe_normalizer.gd` | 只在制作边界转换已支持的正式生产定义；缺规则时返回路径和错误，不运行旧循环、不转换玩家状态 |
| `content_projection.gd` | 模板内容指纹投影；明确区分工时/分数与数量、依赖、端口、阶段等结构事实 |
| `runtime.gd` | 生产份数、依赖完成事实、公共生产/服务推进入口及恢复 |
| `restock.gd` | 共享补货的批次引用和请求；不独立搬运或修改库存 |
| `batch_recipe.gd` | 将每份配比按显式产量修正计算整批请求；在制数量仍只保存于库存operation claim |
| `available_batch.gd` | 从已到位有限原料派生自动批次与后续补料请求；不改变在制批次配比 |
| `production_clock.gd` | 显式加工位速率绑定，复用公共工时公式并在推进/恢复前校验 |
| `numeric_limits.gd` | 从公共修正器派生容量/槽位目标；实际占用仍由库存claim和机器批次持有 |
| `source_demand.gd` | 从生产图、单位完成事实及真实库存/claim派生需求，不保存第二份需求账本 |
| `orders.gd` | 排队、订单明细、生产绑定、交付凭据、付款、座位租约、用餐和离店事实；钱与销量仍使用公共RuleSales |
| `customers.gd` | 顾客位置、路径和真实抵达；不含三种经营模式的分支 |
| `service.gd` / `service_policy.gd` | 编译并组合接单、生产请求、备餐、携带、送达、座位、用餐和真实离店；只保存履约引用和顾客动作时钟 |
| `arrivals.gd` | 固定/随机到店时钟、开张一波顾客、加权菜单请求；不保存第二份随机数状态 |
| `flyers.gd` | 传单待入场人数、间隔/分散节奏与冷却；通过同一Service进客，不持有顾客/RNG/库存 |
| `requirements.gd` | 从外层唯一解锁、料箱、升级和阶段事实判断资格；不复制购买状态 |
| `menu_selection.gd` | 显式菜单顺序、阶段权重、口味组及附加品抽样；只使用外层RNG |
| `waiting.gd` | 只持有顾客与等位端口的租约；人数/阶段/购买事实仍从Orders和外层查询 |
| `customization.gd` | 可选到店选项抽样、显式配方变体和原价倍率；不执行封装动作、不保存第二份库存或RNG |
| `dispatch.gd` | 统一角色/岗位权限；普通搬运、整组搬运、加工与接单均在领取、推进及恢复时检查 |
| `dispatch_leases.gd` | 员工跟随归属和机器阶段租约；只保存身份引用，不复制物品或加工时钟 |
| `view_frame.gd` | 从权威状态生成只读UI/手持/显式展示数据 |
| `scene_frame.gd` | 将公共状态及原钱包/购买事实投影为正式场景可消费的姿态、顾客、活动和机器显示协议，不推进仿真 |
| `processing_display.gd` | 校验台面输入/端口并投影真实加工claim；与货架展示共享同一份物品数量 |

当前生产运行器的owner提供名册、导航、共享属性与修正器接口。受控测试使用既有ShopRules提供这些接口，新核心不读取它的旧库存/serve业务账本。正式切换时要移除旧账本与执行路径，不能长期并行保存两份权威状态。

## 库存契约

```text
reserve → 原库存保持，来源和目标被预留，手持为空
pickup  → 到位动作完成后进入手持，来源空间保留用于取消返还
drop    → 到位动作完成后进入目标，手持与返还空间释放
cancel  → 释放预留；已拿实物回到原位置/归属；无限源领用销账
```

- `reserve_transfer(worker,...)`与`reserve_actor_transfer("customer:<id>",...)`使用同一个实现。员工ID与顾客ID有不同命名空间。
- `hand:<staff id>`、`hand@customer:<id>`是受管理容器，不能通过seed、普通搬运或加工伪造/转移手持。
- 已拿材料继续由原claim占用，不能同时交给另一个任务加工。
- `reserve_operation/complete_operation`原子处理多输入配方。设备内建无限原料也走同一事务，既不生成散落物品，也不虚构员工取料。
- 所有视图默认不画等待库存。`stock_showcase`必须声明展示端口；顾客手持使用同一携带者投影。
- `reserve_bundle(actor,entries,capacity)`整组精确预留；缺一件或容量不足不留半份预留。员工逐站`pickup_bundle_part`，顾客同点`pickup_bundle`；全部拿齐才可整组`drop_bundle`。子claim不能绕过整组生命周期；中途取消一次性归还已取物并释放未取物。
- `CapabilityRunner.transfer_bundle`通过真实RuleActions逐站取货再统一交付；每站可声明`pickup_seconds`，员工手速统一应用。`interact(...,"admit",guest)`通过公共移动/操作计时产生一次完成或取消结果，不接收店铺脚本回调。

## 模板结构

`SpecShopTemplate`声明`places/machines/recipes/restocks/service/dispatch/hop_seconds`。配方的source/process/transfer节点以显式生产者绑定输入；同一编译器处理线性和合流。机器profile声明人工加工、装卸、搅拌和槽位，不提供任意回调。未知能力、无效数量、缺端口、循环和产量不足都会报错。

规则时长复用`RuleNumbers.capability_seconds`：机器修正与工序fixed数据决定基础工时，员工实际手速由人工阶段应用。自动锅和人工机器不能各自另算升级效果。

place可显式用`anchor="boil"`代替字面port；两者互斥。Runtime从当前nav.layout取得实际points/aliases，`post:<id>`引用posts中的独立站位，缺失或无效绑定在编译前报错。纯制作调用`Compiler.compile(template, Compiler.ports_from_layout(layout))`显式提供环境；旧字面port模板的结果与签名保持。机器可另声明work_port，引用已声明的零容量操作端口；装料、搅拌、加工和卸料统一使用该站位，材料仍留在input/output容器。直接操作和恢复也检查同一个站位，不能用任意点替代。

同一设备可进一步声明`stage_ports={"load":"prep:work","operate":"grill:work"}`。只接受实际启用的load/operate/stir/unload，全部引用既有place；显式阶段站位优先，其余阶段继续使用work_port或原输入/输出站位。一个run在不同阶段之间移动时仍占同一个物理槽位，`hold_machine`保留同一员工。未声明或空字典不改变旧定义/快照，直接操作和恢复均验证阶段对应站位。

人工装料/搅拌/卸料可选`stage_timing={"load":{"target":"rear_equipment","fixed":true}}`。基础秒数仍来自profile，公共数值公式应用目标调平；fixed跳过机器速度/时长升级，员工手速只由原人工阶段应用一次。第一次进入阶段时把有效工时提交到原run.stage_total/stage_left，召回或调平改变后不重计已开始的工时。未知参数、空目标及未启用阶段在编译/机器恢复审计时拒绝。operate继续使用配方节点的工时，不接受另一套阶段计时定义。

### 实际煎饼生产配置

`content/shops/pancake/shared_production.tres`包含7款实际餐品及7条`:bag`变体。原1秒固定打糊映射为鏊子的人工load阶段，在`rear_equipment.mix`站位完成；10秒摊饼为同一run的人工operate，移动到原鏊子站位。面糊是这次连续加工的准备阶段，不增加可被其他订单领取的中间库存；原料flour最终由原operation一次消耗，产出pancake一次。鏊子全程只占一个槽位，其他人工工位声明4槽，覆盖原店最后阶段4名员工的并发范围。

薄脆的原4份库存、每锅4份、18秒、人工装卸各2秒和低于3份补货均显式声明。生产在薄脆取货坐标组合`pancake + crisp → pancake_crisp`，不再仅改手持图标；配料为显式安装的integrated供给，family沿用原整体口味物料。卷饼和装袋用公共processing_display展示真实有限投入，完成即清除；装袋明确消费所选餐品并产出bagged，包括原选项可用于单点豆浆的路径。成品实际搬到原前台坐标的各菜收货容器，等待库存不画场景散落图标。

该资源现已组合下文的公共service：实际阶段菜单/解锁、附加豆浆、装袋抽样、队列/购买等位垫、传单和整单结算可在开发期Runtime中验证。显式生产请求仍供制作测试使用，不负责验证顾客菜单资格；玩家顾客请求由service检查。正式SpecShop/UI和玩家存档尚未引用它，其他店的完整顾客配置及三店切换也未完成。`recipe_normalizer.gd`仍是有限的旧定义转换器，完整煎饼使用显式资源，不假装自动理解旧隐式配方。

source节点可声明`timing_target`和`fixed`。指定目标后，取料使用同一公共数值公式；`fixed`跳过机器速度/时长效果，保留目标调平倍率，员工手速由真实拿取动作应用一次。未指定目标的既有模板保持字面工时。生产取料、最终出品描述和服务备餐/送餐共用该计算，不能各自另算。

### 正式配方转换与内容身份

`recipe_normalizer.gd.from_shop(shop, selection=[])`返回`scope=production_only`、`template`和`errors`。它不读店名，不修改正式Resource，不选择旧执行器；有错误时不返回可运行的半份模板。空配方/工位/库存、缺操作端口、参数类型错误均在制作边界报错。

当前可转换小炒饭馆7道显式配方，以及奶茶店`lemonade/lemon_tea`、煎饼摊`soy`的生产子集。实际测试使用原导航、原员工和公共运行器，并在正式交付坐标声明测试收货容器，完成真实取货与放下；它不表示正式服务已经接入。转换结果尚不包含阶段解锁、选项、最终出餐口暂存配置、岗位和旧档转换，不能直接挂到正式入口。

动态备货、设备内建输入的正式绑定、自动工作台批次/时钟、连续工作、台面加工展示、隐式携带变换和空产出的收尾交接尚有能力映射缺口。转换器拒绝这些情况，不能丢步骤或用人工工时替换自动机器时钟。

`ShopContentContract.describe_template(template)`生成独立的玩法和结构SHA256。配方数量/依赖、端口、容量、初始库存、槽位和归属策略是结构；明确列出的工时、分数和客流权重允许数值调平。人工装卸从0变成正数会新增阶段，属于结构变化。仅步骤文案从指纹中排除；名为`seconds`的物品仍保留数量。此接口尚未把模板字段接入正式`SpecShop`或玩家存档，也未实现内容版本采用。

### 公共备货策略

`restocks.<id>`省略`policy`时保持原有整批填库存行为。可显式配置：

```gdscript
"policy": {"mode":"demand", "base":3, "per_waiting":1, "low":0}
```

目标为`min(stock_limit,max(base,未覆盖需求数量×per_waiting))`；实际库存加在制产出低于目标或低水位时才准备整批生产。整批容量、物料、装卸和搅拌仍由公共库存/机器能力控制；目标可以被一整批略微超过，但不能超过库存硬上限，也不能拆批或丢弃超量产出。低水位是触发条件，不表示要填满容器；倍率0明确禁用该项需求增量。默认fill模板不计算额外需求。

`Runtime.source_demand()`是只读投影：输入容器已有材料、已预留/在途搬运和已经开始的加工不会再计缺量；来源型最终出品的有效领取凭据持续覆盖它的生产份数，顾客吃完也不会重新触发旧单。取消领取会重新打开需求，同时由原库存事务归还实物。需求策略首批只接受一种库存产物，且整批不能超过配置的库存上限，避免混合批次掩盖单项缺料或空仓时越界启动；未知字段和策略报错，不能挂店铺回调。

柜台递餐/送桌的候选同时检查该份出品是否已经在顾客容器或被另一员工预留配送，避免共享库存还有余量时，两名员工重复配送同一份生产绑定。不同份数仍可由不同员工协作。

此能力尚未自动采用旧奶茶店stock中的`base/per_waiting`：核查发现旧handoff循环实际按输入容量、整批启动和工单推进，没有消费这两个字段。正式迁移必须按真实行为显式配置并对照轨迹，不能按注释直接替换。

### 每份配比与每锅份数

共享补货可声明可选批量绑定：

```gdscript
"consumes": {"leaf":1}, "produces": {"tea":1}, "sources": {"leaf":"pantry"},
"batch": {"target":"pot", "base":3, "max":8},
"fetch_seconds":0.6, "fetch_timing_target":"pantry", "fetch_fixed":false
```

声明batch后，consumes/produces是每份配比。公共`batch`修正器在开锅前计算整批投入与产出，员工按真实容量分次搬齐材料后才开锅；每锅工时仍由seconds及公共工时公式决定。max必须同时满足已声明输入/输出容器、库存上限与整数表示范围，不能靠溢出或截断取整。没有batch绑定时，原数量和编译签名保持原样。

开锅后以原库存operation claim中的配比为准，途中升级不改旧锅数量；下一锅才应用新份数。恢复校验实际配比是合法的整批整数倍且在声明范围内，不要求旧锅数量等于当前升级值，也不另存数量账本。fetch_timing_target/fetch_fixed使补货取料复用公共工时和员工手速；fixed=true必须声明目标，不能静默忽略。

奶茶共享锅组合测试使用原导航、员工、30秒煮茶、两次搅拌和人工装卸。原开局batch基础效果为2，覆盖缺省基数3；测试先做2份、取走1份，再用显式修正做6份，原料总消耗8份。卸料工时按旧handoff真实使用的hop_seconds显式声明。这仅验证共享锅子流程，尚不包括原料箱采购/解锁、旧派活顺序、完整配方和正式服务入口；运行时扩容/槽位升级须另行声明下方的数值绑定。

自动工作台可声明`batch={"mode":"available","max":6}`，consumes/produces仍是每份配比。必须有有限投入，max满足输入/输出和库存范围；实际批次按已到位可用原料、整份比例与真实输出余量取值。到位两份就同批做两份，不等待max，也不为每份新建时钟。加工期间可继续按需求补入后续有限原料，在制claim保持原数量；新到原料由下一批使用。已经到位的有限投入可以完成加工，需求策略只控制新取料，不把原料凭空移回。普通固定/数值批量模式保持原语义。

process节点可选`slot_rate={"target":"seal","base":1,"max":6,"ignore_duration":true}`，显式用公共process_slots值除工时，与profile.slots的同时在制数量分开。用于保留旧封口机“9秒÷加工位数”的实际速率语义；ignore_duration明确保留其只受speed、速率和目标调平影响的规则。数值须在范围内为正整数，非法值在初始化、推进或采用存档前拒绝；在制工时继续由原machine run持有，途中升级只影响新开始的加工。

### 奶茶实际生产模板

`content/shops/tea/shared_production.tres`是实际店铺的显式生产数据：8款普通饮品和6款封口变体，包含茶叶实物搬运、30秒共享锅/两次搅拌/人工装卸、4秒按到位原料成批调奶、人工加料、普通出餐口、封口和外带架。端口引用原店layout，煮茶/加料使用独立post站位；前台与后厨权限由同一公共dispatch数据声明。该文件没有店铺执行代码或脚本回调。

共享锅使用旧运行状态实际保存的black_tea物品；旧SpecStep中tea到black_tea的隐式改名在新数据里明确为同一共享茶汤来源。调奶每份明确消费black_tea+内建milk，并在同一个6份容器配额中加工；原始奶茶成为加料和出餐的共享来源。该配置没有复用旧SpecStockRule中未被执行的base/per_waiting字段。

验收按原公开命令开设备、安装茶叶/牛奶箱、开放口味、招募和派出后厨员工；保留原前台岗位及全局角色属性，未让开局唯一的前台跨过岗位权限去做后厨。八款逐道产出、六款封口/外带架、整菜单波次在搅拌/调奶中恢复，以及前台真实取杯送柜台均使用同一个Runtime。

这是全设备已开的生产配置，不含正式阶段菜单、坐班专属策略、到店/接单抽样、堂食/外带顾客分流、旧档转换或正式UI入口。服务/制作转换器仍保留各自明确的缺口门禁；原SpecShop、场景和旧运行入口未修改。新模板的同容器机内总量应读取同一frame.stock，不把input/output对同一容器的引用重复相加。

### 明确声明设备内建供料

设备输入容器先声明已安装的供料，例如`places.mix_in.infinite=["milk"]`；配方再明确绑定：

```gdscript
"consumes": {"tea":1, "milk":1},
"inputs": {"tea":"tea_source", "milk":{"capability":"integrated"}}
```

只有严格的integrated绑定和该机器输入容器的安装声明同时存在才有效。缺绑定不会自动推断；供料未安装、未知键和回调均编译失败。茶仍从生产者实际搬到机器，牛奶不增加虚构来源节点、员工拿取任务或手持图标；生成与消耗在已有库存operation完成时一次性记账，取消和恢复共用原事务。

内建输入不计入物料搬运需求或生产者依赖。相同库存能力也支持共享补货中的内建配料，并随batch份数缩放；不新增数量表。普通来源绑定和未启用能力的模板保持原编译结果。

`tests/fixtures/template_tea_production.gd`是制作期生产子流程：原导航/名册、2份共享煮茶、实际搬茶、内建牛奶与4秒自动调制。它假定材料已安装，不负责采购/解锁、正式出餐口、封口、岗位和完整店铺接入。

### 容器容量与机器并行槽位

容量和槽位可独立声明公共数值绑定：

```gdscript
places.shelf = {"port":Vector2(100,100), "capacity":4,
    "capacity_binding":{"target":"shelf_upgrade", "max":8}}
machines.mixer = {"input":"mix_in", "output":"shelf", "profile":{"slots":1},
    "slots_binding":{"target":"mixer_upgrade", "max":3}}
```

基础值来自capacity/profile.slots，分别读取外层公共capacity/process_slots修正。目标必须是声明max以内的有限整数；容量允许0，槽位至少1，不截断小数。绑定缺省或为空不增加编译字段和签名；无上限容器不能声明容量绑定。补货整批范围按声明max校验，运行时仍须满足实际可用容量，不因预留了未来升级范围而提前扩容。

扩容允许真实新增库存/并行加工；缩容保留实物、输入/输出预留、手持物的返还空间及在制批次。有效上限为max(新目标,实际占用)，占用超过目标期间阻止新增占用，原工作照常完成；普通及整组交付、取消和加工完成后立即收敛，不等待下一帧。输入/输出共用容器时仍只有一份容量。

目标缓存是派生策略，库存和机器快照仍使用version=1，不增加数量账本。恢复仅放宽已声明绑定的容量/槽位数值，并检查范围；端口、无限供料、其他profile和未绑定定义仍严格匹配，全部验证通过后才采用演员。外层负责恢复修正器，再恢复运行器。暂停不应用新目标；非法目标在推进时间或部分扩容前返回错误。

`Runtime.frame().limits.capacity/slots[id]`暴露target/applied/used用于诊断，不保存第二份占用。此能力尚未映射正式三店升级；旧正式入口的校验器明确拒绝capacity效果，防止制作数据被静默忽略。

### 配方中的实物交接

已有成品搬到另一容器，用transfer节点表达，不用一次消耗/重产的加工假装搬运：

```gdscript
{"id":"to_pass", "capability":"transfer", "input":"mix",
    "place":"pass", "item":"milk_tea", "count":1, "seconds":0.6}
```

input是已有生产者节点，place是目标容器；物品、数量和归属随真实搬运保持，不改变created/consumed账本。编译器校验生产者、物品、数量、容量声明和依赖，禁止同容器搬运、无限供料目标、未知字段和回调。count缺省为1，多件请求作为整组精确领取，物料/目标容量/员工容量不足时整组等待，不提交半份终端交接。

领取候选复用公共整组搬运、派活权限、路径和动作。拿取工时来自生产者，seconds是目标放下工时；可选timing_target/fixed复用公共数值公式，员工手速仍只应用一次。未声明目标时使用字面工时；fixed=true必须有目标。预留不显示手持，真实拿取后才显示，放下后清除；等待库存默认只有UI统计。

unit.running只引用原bundle ID，真实drop凭据决定节点完成；取消归还实物并允许重新领取。恢复检查唯一bundle、源/目标、物品/数量、原归属/新归属、依赖和完成事实，再采用演员。快照仍使用既有version=1结构。机器与bundle编号各按节点能力解释，不能拿一个交付凭据完成两道工序。

transfer可位于配方末尾，也可继续输入普通process完成封装等明确变换。需求投影区分内部图搬运和最终顾客领取，已完成交接不会因食物被后续消耗而重新备货。柜台、自取、送桌继续读取相同的最终出品描述，无新增服务执行器；未声明transfer的模板编译结果和签名保持。

此能力不自动转换旧配方中空produces，也不代表封口/装袋选项已迁移。旧pickup还包含堂食/外带分区、封口时钟和容量；旧装袋还有抽样、价格和隐式换物/台面展示，均须后续显式映射。奶茶验证只在已安装原料的生产子模板后接一段到原seal坐标的实物搬运，不是正式三店入口切换。

### 台面加工展示

机器可选声明加工中原料的展示；省略或空字典时保留原编译结果、签名和机器快照形状：

```gdscript
machines.roll.processing_display = {
    "capability":"processing_item", "items":["pancake","crisp_pancake"],
    "points":[Vector2(400,300)], "host":"roll_table"
}
```

items列出允许展示的有限投入物，每次加工最多匹配一个；points明确每个并行槽位的显示坐标，必须覆盖profile.slots和slots_binding.max；host是显式排序宿主。原料未被声明配方/补货使用、物品重复、无限供料、同一加工匹配多种输入、缺端口和未知键/回调都在制作时拒绝。其他配方未匹配items时仍用普通库存UI，不显示附近另一份等待原料。

输入实际放入容器并被加工operation预留后，从claim.parts取得显示物品及数量。等待员工操作、自动加工、搅拌、卸料期间保留同一真实输入，完成/取消立即移除；未开始加工的等待库存与已完成产品默认只在UI记录。手持量仍来自原库存：运输时画手持，到位放下后清除，再显示对应加工输入。展示不推进机器、不消费/生成物品，也不保存进度或可见物品列表。

启用能力后，机器定义保存静态slot_ceiling，运行批次保存slot整数引用。新批次领取空闲编号，完成/取消释放，仍在制的批次保持原编号；槽位升级、缩回、暂停、召回和恢复都不会重排。并发数量仍使用原process_slots和真实占用，端口编号范围独立于并发数量：缩至1时仍可保留原slot=1的批次，新工作按新数量等待或领取空闲低编号。

加工展示与stock_showcase同时启用时，投影从货架绘制中排除已经画到台面的那部分lot数量，不重复画同一份原料；库存UI始终记录完整权威数量。Runtime.frame()自动合并已编译的绑定与额外展示参数，冲突返回error并清空draws，不回退到操作坐标。加工draw包含machine/run/slot/item/count/pos/host；字段全部派生，修改返回帧不改规则状态。

恢复严格校验slot形状、静态范围、活动批次占位唯一性及原库存/机器事务，再采用演员。旧未启用机器仍没有slot_ceiling/slot字段，私有快照继续使用version=1。此批提供公共投影，正式场景消费这些draw和旧put_down工序的配方/端口转换仍待接入；旧卷饼/装袋显示路径尚未替换。

## 公共服务配置（受控模板已接通）

`service`为空的模板只运行生产；声明后由同一个`Runtime.step`组合整个服务周期：

```gdscript
service = {
    "menu": {"dish_id": "recipe_id"},
    "admission": "employee", "admission_port": "front", "admission_seconds": 0.6,
    "admission_roles": ["staff"],
    "delivery": "self_pickup", "pickup": "pass", "customer_capacity": 2,
    "delivery_roles": ["staff"],
    "seats": {"seat:dine/0": "table_staff_port"}, "eat_seconds": 3.0,
    "orders": {"pay_at": "on_deliver", "queue_release": "after_take"}
}
```

- 菜单引用现有菜品价格接口和模板配方；报价在真正接单时获取。当前服务配方每份最终出品数量必须为1；机器内部仍可批量加工。不能静默把多件出品算成一件销售。
- `automatic/employee`只决定是否由员工在接单端口完成工时。顾客必须实际抵达队首，取消员工接单不能创建订单或收费。
- `counter`声明`handoff_port`，顾客到达`pickup`后员工可分批交付；最后一份交付后按订单策略结算。`table`使用具名座位和员工桌边端口，必须等顾客真正就座。
- `self_pickup`由员工备齐取餐点库存，顾客实际到位并完成取货工时后整单拿起，携带到具名座位/出口再放下。顾客携餐时不再为同一订单重复备货；取餐点已有的成品可以直接使用，无需虚构员工搬运。
- 座位目前从接单持有至顾客真正离店，满座会保留顾客在队列等候。用餐结束逐生产份数通过公共加工事务消耗食物，保留可恢复的消耗凭据。
- 员工资格与实际移动使用同一`access_profile`；未配置角色名单时可由所有部署员工承担相应服务任务。生产、补货、接单和交付现由同一候选池排序，跟单和机器阶段持有按下方公共策略配置。
- `Runtime.arrive([{dish,qty},...])`仍可显式输入顾客；自动客流须另行声明下方能力。正式升级门槛仍需在正式入口切换时组合。

## 客流与岗位配置

### 队列与等位端口

可选`service.waiting={group,ports,line,stages,retain_after_take}`声明公共等位能力。group引用外层purpose=wait的购买组，ports列出该组已有的`wait:<group>/<index>`顾客目标，line为全部实际站立坐标，stages逐阶段声明`{standing,seats}`。有效等位数量=min(外层已购买数,本阶段开放数)，排队上限为站位数加有效等位数，并受声明物理位置及仍在等位的已接单人数约束。字段、端口或购买事实无效时明确报错，不补坐标、不改原场景布局，也不调用旧店顾客控制器。

未接单的溢出客人获得不同等位端口；已分配者在队伍前移时保留原位。retain_after_take=true供柜台服务使用，已接单的顾客优先分配等位处等待制作；false可用于送桌，接单后释放等位名额并去用餐目标。两者均要求订单在接单后离队。人数或阶段上限下降时已有租约继续保留，新客按新上限拒绝，空出来的位置不越过新上限复用。

租约只存`{guest,port}`，不复制订单/人数/钱包/路径。员工实际领取接单任务时，原guest.claimed事实把顾客叫到queue:0；领取递餐任务或开始分次交付后，顾客才离开等位处去pickup。员工与顾客各走原公共移动，接单工作和递餐放下都必须等待两者到达真实端口；无路则等待，召回仍用原库存取消补偿。候选查询不分配等位名额或移动顾客，暂停同时冻结动作与位置。

启用时公共服务帧/快照增加waiting租约及派生queue_capacity，Customers仅接受已声明的waiting_line端口；未启用时定义、快照与老模板签名保留。恢复交叉验证原Orders状态、唯一租约、顾客动作目标和实际交付凭据，重复/未知/失效引用在采用演员前拒绝。租约不代表角色已经坐下，显示应同时依据顾客实际位置与抵达状态。

煎饼数据保留原3/4/4/6/6个站位、0/2/5/9/9个阶段等位上限，以及公开命令的2/3/4张坐垫购买。九个等位目标直接引用原customer_points；站立缓冲显式声明原八点和原队列延伸的两个已核对坐标，运行时不会外推到缺失位置。没有购买坐垫时不会获得等位容量。

### 传单客流

可选`service.flyers`与现有arrivals/menu组合。`pattern="gap"`声明正数gap和可选first_delay（缺省0），发出后下一个仿真tick尝试首位，再按固定间隔逐位尝试；允许冷却结束后追加新波，原待入场人数保留，新命令重置首位节奏。`pattern="spread"`声明正数seconds，间隔为seconds÷当前公共flyer_customers，持续读取人数升级改变后续节奏，但不凭空增加已批准的一波人数；波次时钟和冷却都结束后才能再次发出。两种策略都每tick最多尝试一位，计时跨阈值后从本次尝试重新计时。

count/cooldown是无效果时的基础值，实际人数与冷却复用已有flyer_customers/flyer_cooldown公共修正。人数必须为正的安全整数，冷却非负且有限；无效修正在时钟/演员推进或恢复前拒绝，不能默默截断小数。已开始的冷却不因升级重算，新的命令才使用新人数/新冷却。关店保持待入场人数和入场计时，未暂停的仿真仍推进冷却/波次禁发时钟；暂停冻结全部。

when_full可选lost或wait_outside：前者消耗这位传单客人、通过原Orders记录一次流失；后者保持待入场且不记流失，空间真正释放后再尝试。满队和空菜单均不抽废弃的主菜/附加品/选项随机数。传单尝试排在同tick普通到店之前；普通到店时钟、尝试计数与RNG间隔抽样仍由原Arrivals持有，不因发传单重置。真正进入时继续调用同一Service.arrive，走菜单门槛、选项、等待、生产、实物交付与整单付款。

开发期入口是`Runtime.send_flyers()`，成功后才在公共事件总线发flyer，观察者看到的是已提交状态；回调保存/恢复与再次发送受原冷却约束。新能力不调用旧ShopRules.send_flyers，不写flyer_left等旧运行状态。快照只保存待入场与时钟，不保存另一份顾客或RNG；恢复拒绝负数、非法时钟和无关字段。能力为空/省略时不增加编译字段/帧/快照，不抽随机数。

实际煎饼声明gap=3、when_full=lost，沿用原基础4人/120秒及公开flyer升级轨的5人/105秒、6人/90秒等效果。奶茶式30秒分散入场/店外等待已由同一能力支持和组合测试验证，正式奶茶顾客配置尚待接入；正式按钮和旧档仍须在U06切换时连接新入口。

### 菜单资格、阶段权重和附加品

`service.selection`可选，空/省略保持旧编译签名。`order`明确全部菜品的抽样顺序；`gates`为每道菜声明可选`stations`、`boxes`、`levels={track:minimum}`和最低`stage`。运行器只读外层命令已持有的解锁/购买/等级事实，初始化检查未知工位、料箱和升级轨，当前阶段越界在推进时钟、动作或采用存档前拒绝。显式顾客请求也检查资格，失败不增加流失、不抽RNG；已经冻结的历史请求不因后续关闭门槛而重抽或无法恢复。

`stages=[{interval,weights},...]`按外层stage_index选择阶段，`groups=[{id,dishes,fallback},...]`把组权重平分给已开放成员，没有开放成员则并给明确的fallback。直接菜按order先抽，组成员按groups内数组顺序接在后面；不依赖Resource字典保存顺序。门槛变化只影响新请求，当前到店倒计时不重置，下一次调度才使用新阶段间隔与公共flow/调平。

可选`addon={dish,share,first}`先抽主菜，再对不同且可用的附加菜抽一次概率，之后复用公共customization抽主菜选项。first=true只改变生产份数创建顺序，附加菜先制作；请求/报价仍以主菜为第一行。满队跳过菜单/附加品/选项；空菜单不抽这些随机数且不记流失，指数到店时钟自身仍可抽下一间隔。相同附加菜、未开放附加菜不抽附加概率；有效0/1概率仍抽一次。

启用selection后，`service.arrivals`只声明pattern/first_delay/opening，省略choices且不能另写interval；否则制作报错，防止同一间隔有两处配置却只消费一处。整单自取容量不足以容纳可能的附加品时也在制作阶段拒绝。时长/权重/附加概率属于可调数值，顺序、分组、资格和附加品先后策略仍属于结构身份。

菜单可选声明`ramp={start:0.25,orders:12}`：每次成功到店，对当时权重表中**全部可售菜品**各增加一次曝光，直接菜品权重乘`lerp(start,1,count/orders)`，到orders次封顶；orders=0为不缩放。组份额及其fallback在直接权重缩放后分配，不乘爬坡，但已分到份额的成员仍积累曝光。开张、普通到店、传单与显式到店共用同一提交；满队、空菜单、非法请求不增加曝光，已选餐品不重抽。它不是销量计数，不按选中的菜单独增长，也不写外层旧order_ramp。`Service.menu_weights()`返回当前权重的脱离状态查询。

可选`selection.flow={flavors:[dish_ids],per_extra_flavor:0.12,stations:[station_ids],per_level:0.0}`显式声明客流贡献：可售口味数超出第一个的部分，与已解锁设备超出初始等级的部分分别相乘，再调用公共flow效果一次；最后仍通过RuleNumbers.flow_interval调度唯一普通到店时钟。flavors使用同一gates，stations必须有已声明的升级轨；不读取店名、旧模式或自动遍历旧设备能力。门槛、等级、效果改变只影响下次调度，已提交倒计时保持；非法/非有限倍率及派生间隔在任何运行状态推进前拒绝。

ramp仅持有每道菜单的有界曝光计数；顾客、订单、随机数和财务仍由原组件唯一持有。快照只在启用时增加ramp；恢复拒绝未知菜、非整数、负数、超出曲线封顶或超过历史成功到店总数的曝光。省略ramp/flow保持既有编译签名与快照形状。曲线与客流系数为可调数值，贡献菜品/设备身份及能力启用仍是结构；同版本严格恢复不等于已经完成内容迁移。

奶茶六阶段菜单算术已与原规则查询逐次对照，实际shared_production资源现已声明同一套菜单、人员可售资格及下述柜台堂食/外带组合。正式入口没有切换。

### 柜台交付后的堂食与外带

可选`service.dining={group,order,stages,takeaway}`组合柜台交付与顾客后续路线：group引用外层可购买堂食组，order显式列出`seat:<group>/<index>`顾客端口，stages声明`{standing,seconds}`，takeaway可声明`{requires,variants}`。此组合要求automatic接单、counter交付、on_deliver收款及after_delivery队列释放，不与waiting、自取/送桌、customization或另一份eat_seconds混配；堂食顾客端口只在dining.order声明，不需要虚构员工送桌端口。

顾客到店后先分配已购买的空座并创建公共生产订单，走到座位等候；座满且外带门槛已满足，则选择明确的变体生产图并站队等候。座满而外带未开放时，已选菜品留在队列，尚不提交生产路线；以后扩座/座位释放优先将最早等待者转为堂食，否则在外带开放后转为外带。这一边界只冻结dish/qty，直到路线确定才冻结recipe/item并创建生产份数；不会先造一份普通单位再另造封装单位。已接受的路线不因门槛随后关闭而重写。

员工领取真实递餐任务并预留库存后才把顾客叫到pickup；公共动作在双方实际到位前不放货、不付款。交付的库存容器仍为`guest:<id>`，其员工端口始终是柜台；堂食客人交杯后沿公共移动返回原座，真正到位才开始吃，外带客人走出口。整单交付时固定当时阶段及seat调平的用餐时长，返座途中不消耗，后续换阶段不改这份时长。用餐结束即可将座位让给下一位，原客人继续真实离店。

座位唯一保存在Orders.guest.seat；dining快照只记录`{guest,takeaway}`路线选择，不复制座位、人数、路径、库存或钱包。队列容量从当前阶段standing加仍排队的占座订单派生，站位索引只计未占座者；买座、升级仍由原命令持有。恢复交叉检查路线/座位/配方/实际生产绑定/目标/库存交付，允许已交付客人正在回座，吃饭状态仍要求真实到位；未知或未购买座、重复租约、孤立路线、非法或超出全部阶段/调平上限的用餐时钟均拒绝。

共享资格可选`workers={minimum:1,exclude_posts:[post_ids]}`，只计实际已部署且不在排除岗位的员工；不会将“已招募、未部署”当作产能。最低数及岗位身份保留结构身份，未启用不增加原编译字段。奶茶的非前台菜和共享后厨备货使用此能力，并继续受设备、料箱和口味等级门槛约束。

奶茶实际模板现含八款主菜单、六条封口变体、六阶段菜单/座位工时、开张三人和原30秒分散传单。新能力没有调用旧经营循环；但外层旧unlock命令本身仍可能生成旧开张订单，正式U06切换必须移除这项副作用，同时迁移旧档和正式UI。开发期夹具明确处理这些命令侧事实，不能将新Runtime的通过当成正式旧档或网页已经迁移。

共享补货可独立声明`restocks.<id>.requires`，使用相同资格语法。未满足条件不启动新批次或取新料；已开始批次保留原事务、工时和人工阶段。煎饼油锅因此只在真正解锁后补货，开局保留原4份薄脆但不会暗中运行关闭设备。

员工递餐可选`service.delivery_ready="whole_order"`，整单剩余实际出品全部可领取后才安排第一趟；每趟仍受员工真实容量限制，预留/携带/放下及收款使用原公共能力。默认仍按已有可用出品派送，整单自取已自带齐备条件，不能重复写此参数。煎饼启用此策略，在主菜装袋和普通豆浆都准备好后递餐，只在全部交付后收款；不另增店铺专属派单循环。

### 订单选项与配方变体

`service.customization`可选；省略或空字典时，原定义、签名和请求/订单形状保持。启用后声明选项及每个组合对应的普通配方：

```gdscript
service.customization = {
    "options":[{"id":"bag", "unlock":"bag_station", "share":0.4, "price_mult":1.25}],
    "variants":{"dish_id":[{"options":["bag"], "recipe":"bagged_recipe"}]}
}
```

请求第一行是主菜，其余行为附加品；选项只作用于第一行，qty>1时每份都使用该变体和单价。某菜品有变体才参与对应选项抽样。unlock引用外层已声明工位，开放查询复用公共station_unlocked；未知工位在运行实例创建时拒绝。首批最多8种选项，每道菜必须为所有适用选项的非空子集声明一个明确配方；未知、重复、遗漏组合和未用选项均报错，不在运行中猜测如何拼接工序。

`Runtime.arrive(request)`在到店时按声明顺序抽样，复用外层唯一RNG。满队、选项不适用或工位未开不抽选项随机数；已开放且适用的概率0/1选项仍抽一次，保持旧语义。`Runtime.arrive(request,["bag"])`明确指定选项，`[]`明确不选，均不抽样；非法/重复/未开放选项在统计到店或流失前被拒绝。自动客流先抽菜单，再走相同选项路径，不额外保存RNG。

选中的ID按声明顺序保存在第一行request/line的可选options数组；未选也保存空数组。接单和恢复不重抽、不因工位随后关闭而清空历史选择。恢复交叉检查已声明组合、配方、最终物品和订单行；篡改、缺失或非规范顺序在采用演员前拒绝。没有此能力的历史模板不接受无来源的options字段。

首批显式要求`service.orders.rounding="order_round"`：接单时通过公共RuleNumbers.raw_price查询主菜原价，再按已选倍率相乘；附加品仍用各自原价，最终通过共享结算整单取整。报价按行索引传给Orders，避免同一道菜同时作为主菜和附加品时覆盖不同价格。报价、实际物品和销量身份分开：变体可产出packed_item，销售仍计原dish；不会为包装另计一份销量。选项概率/倍率是内容数值项，配方、组合和解锁绑定仍是结构项。

变体是原process/transfer依赖图，柜台、自取、送桌共用相同生产与履约；新模块不解释SpecStep、不生成回调或另一套封口/装袋循环。此能力不等于已转换正式奶茶封口和煎饼装袋：台面加工展示、隐式携带变换、正式门槛/配方/旧档和三店入口仍须接入。

自动客流是`service.arrivals`的可选能力，默认不创建时钟、不消耗随机数。示例：

```gdscript
"arrivals": {
    "pattern": "exponential", "interval": 8.0, "first_delay": 2.0, "opening": 1,
    "choices": [
        {"weight": 3.0, "request": [{"dish": "dish_id", "qty": 1}]},
        {"weight": 1.0, "request": [{"dish": "dish_id", "qty": 1}, {"dish": "side_id", "qty": 1}]}
    ]
}
```

由`Runtime.set_service_open(true)`开放，首次开放只生成一次`opening`波次；关闭暂停到店时钟，重开保留剩余等待。间隔使用公共`RuleNumbers.flow_interval`应用客流倍率和调节值，固定间隔本身不抽随机数；指数间隔与菜单抽样复用`RuleSampling`，旧实现也调用同一公式且奶茶冻结轨迹不变。满队只记录流失，不抽一个随后丢弃的菜单。自动顾客仍走相同的订单、生产和履约能力。

随机数由外层唯一`owner.rng`持有，客流快照只保存开关、剩余时间和尝试次数。完整会话保存必须同时由外层保存RNG一次；不能只恢复客流计时器就承诺相同后续订单。抽样默认在到店时完成，可显式使用下述admission时机；阶段权重、菜单爬坡和传单仍走同一公共能力。

### 接单完成时选菜与购买座位池

`selection.at="admission"`让顾客以空request进店/排队，普通到店、开张、传单和显式`Runtime.arrive([])`均不抽菜、不创建订单或生产；显式提前给菜或选项会被拒绝。真正接单完成，且有可用座位/菜单时，才按当时的阶段与资格依次抽主菜、附加品、选项，并经公共Orders一次提交请求和订单。领取接单任务时仍不抽；排队期间解锁/换阶段影响最后抽样，已接受的请求继续冻结。默认或显式arrival保持原默认编译结果。

空菜单仍可接收未选菜的排队客人，但不派无效接单任务。员工工作期间菜单变空则释放该次接单认领和租约，顾客继续等候，不抽废弃菜单；恢复资格后可重新接单。队满、耐心离队、召回及恢复均不能生成早选请求。可选ramp在这种模板中只按成功完成的菜单选择增长，恢复上限按真实已接受订单数验证；默认arrival模板仍按成功进店增长。报价验证失败不会留下半份选中请求，空请求也不能绕过公共Orders生成空订单或进入用餐状态。

`selection.addon.with=[primary_ids...]`可限定哪些主菜允许附加品，不在列表的主菜不抽附加概率；省略列表保持原行为。是否同属前台/后厨由资源明确列出主菜身份，公共抽样器不读取店名或职能类别。第三店酸梅汤因此不隐式获取例汤；盖饭和炒饭继续按原0.4概率附汤。

`service.seating={group,order,stages:[{standing,seconds},...]}`为table/self_pickup服务选择外层购买池和阶段队列/用餐时长。order必须覆盖完整service.seats并按座号列出，只有已买的前缀可用；扩座沿用原购买命令，不保存另一份租约或容量。顾客吃完即可释放座位并继续离店。该配置不能与dining、waiting或另一份eat_seconds混用，时长为可调数值，队列容量及座位身份为结构。未启用时仍保留原固定座位/时长和编译签名。

实际小炒饭馆shared_production已显式声明七道原生产图、两支合流、后厨共享饭/汤备货、前台酸梅汤、六阶段菜单/门槛、接单完成时抽样、六人队列、六至十六个可购座位、整单自取及原传单。制作时转换器只生成数据，正式新Runtime不调用旧ServeFlow或运行时规范化器。取餐等候及坐班岗位按下述公共能力接入；当前正式ShopRules入口与画面仍未切换，剩余岗位/搬运规则及正式存档/展示仍需后续组合验收。

### 取餐排位与物理岗位占用

核对旧CustomerMovement后，第三店取餐点实际按**等候顺序**分配，并不固定绑定餐桌座号。公共`service.pickup_queue={ports:["pickup:0",...]}`为self_pickup显式声明有序顾客端口，需覆盖完整座位池，端口及物理位置均不可重复。第三店复用已有16个取餐端口，没有修改原场景布局。

排位由Orders中仍等待取餐的顾客顺序及已有交付phase派生，不新增租约、人数、库存、路径或随机数状态。预留整单、取餐计时中的collect仍占当前位置；实际pickup提交并进入carry后才退出队列，后面的人沿公共移动向前。客人可在自己的等候点取走已经齐备的整单，不强制等队首先出餐；正在走向新排位的人暂停取餐计时，到位后才提交实物拿取。等待、collect、前移中的保存恢复按同一事实校验目标，错误/失效目标拒绝采用。`frame.pickup_targets`只是脱离状态的派生显示，快照不另存一份排位；未启用能力保持原pickup默认目标和编译字段。seating服务帧也暴露与接单一致的queue_capacity。

公共`dispatch.station_posts={machine:{post,feed}}`将物理岗位与设备绑定：有实际部署员工在岗时，其他人不能操作该设备，跨批次仍受该占用约束；无人坐班后按原角色权限恢复流动工作。feed=true另限制向该设备唯一输入口投料，普通搬运和整组搬运都走同一权限检查；feed=false允许协作送料。绑定必须对应已声明机器、岗位权限及真实岗位锚点，多人占同一物理岗位在推进/恢复前报错。

占岗事实来自外层实际员工post，不另存岗位租约。调岗改变权限时，原操作/搬运仍由公共Runner在推进机器时钟前撤销并释放；机器进度和原有同批次hold_machine租约仍由已有能力持有。奶茶显式补齐boil/topping岗位，煮茶工自己送料、加料工允许流动员工供料；第三店补齐wok_a/wok_b岗位，仅坐班者操作，流动员工可送原料并装盘。未启用时不增加编译字段或状态。此能力补的是物理占岗，不代表剩余前后厅协助优先级和跨生产份数的批量搬运已全部映射。

`dispatch`允许声明`roles`（移动权限profile）和`posts`（岗位ID）。两者都为空时保留原公共运行器的可执行范围；声明某角色或岗位后，未列出的能力默认禁止。岗位定义覆盖角色；一旦声明岗位表，未列出的非空岗位不获得其他角色的权限。

```gdscript
dispatch = {
    "roles": {"staff": {"operate": ["*"], "transfer_from": ["*"], "transfer_to": ["*"], "interact": ["front"]}},
    "posts": {"device_post": {"operate": ["device_id"]}}
}
```

`operate`引用设备，`transfer_from/transfer_to/interact`引用声明的端口，`*`为明确授权全部。整组搬运必须同时具有每个取货端口和交付端口的权限；不能由某个子项绕开。实际执行器在创建库存claim前检查，直接调用也不能绕开；推进前重新核对岗位和移动profile，失效时统一取消/归还/释放机器，且不再推进已移走员工的人工时钟。恢复也检查当前外层岗位。

## 公共派活与租约

生产、补货、接单、备餐和员工交付只产生标准能力候选，唯一员工分配循环调用同一个`Dispatch.rank`再领取。服务组件不再另外遍历员工分配任务。`Runtime.candidates_for(worker)`返回脱离权威状态的候选，可用于诊断，不预留物品、不推进时钟、不抽随机数。

```gdscript
dispatch = {
    "affinity": "exclusive", "affinity_bonus": 100.0,
    "continuation_bonus": 20.0, "travel_penalty": 0.01,
    "hold_machine": true, "help_while_waiting": true,
    "scores": {"admit": 400.0, "deliver": 300.0, "stage": 250.0,
        "operate": 200.0, "transfer": 100.0,
        "restock_operate": 200.0, "restock_transfer": 100.0}
}
```

- 同分保留原候选顺序；实际已完成工序触发`continuation_bonus`，真实导航路径长度按`motion_units`归一后应用路程扣分。无路的候选不抢占员工，直接请求仍由公共移动保持阻塞，不回退直线穿越。
- `affinity=none`为默认；`prefer`优先继续本人的同单工作但允许其他员工协助；`exclusive`让一名员工从接单、主餐/配餐生产跟到交付。接单租约从`guest:<id>`晋升为`order:<id>`；没有顾客绑定的手动生产请求以`unit:<id>`跟随至生产完成。跨职责合作的店铺应选择与权限配置相容的策略，不能把exclusive当成任意分工下的加速选项。
- 跟随归属从真实claim分片、原所有者和分配所有者推导；省略owner或改用整组搬运不能绕过。exclusive不允许混合不同订单的整组，失败时整份候选库存不采用，不留半份预留。共享无归属杂活可在允许协助时执行，原跟单租约仍保持。
- `hold_machine=true`保留同一机器运行批次的装料、自动等待、搅拌、卸料阶段给原员工；其他员工不能抢走后续阶段。`help_while_waiting`决定其等待期间能否协助；已持有机器需要人工阶段时优先返回。一个员工持有多锅时，可以继续任意一锅，不能互相卡死。
- 订单交付、独立生产完成或机器批次结束自动释放相应租约；召回、调岗、区域变化或取消也释放，保留已发生的库存/收入事实与机器剩余工时。持有期间空闲的员工也要释放租约，不依赖是否正有动作程序。
- 快照保存跟随/机器租约和任务scope；恢复先交叉校验真实物品归属、订单绑定、机器运行和当前外层员工身份，再采用演员。未知/重复租约、伪造scope、丢失活动操作员租约均拒绝；已完成来源的后续搬运不会生成过期租约。

机器阶段持有与物理坐班是两种公共约束：前者保留同一运行批次，后者由`station_posts`读取实际在岗员工，在多个批次间限制操作及可选送料。正式奶茶派活顺序仍须在正式入口切换后做冻结轨迹/画面对照验收。

可选`dispatch.assistance`在`roles`或`posts`下给已声明的本职权限增加搬运协助：

```gdscript
"assistance": {"posts": {"counter": {
    "transfer_from": ["pantry", "kitchen_out"],
    "transfer_to": ["kitchen_in", "window"],
    "wait_for_admission": true
}}},
"batch_transfers": true
```

- 先筛出可领取、有路且符合跟单/坐班约束的本职工作；存在本职工作时不生成协助。已被同事领取的加工和库存/容量不足的整组不算可领取工作。协助只增加普通/整组搬运，不增加加工或接单权限。
- `wait_for_admission`使有资格接单的员工为将要到达的客人留守；满座无法接待或菜单为空时不徒劳留守。正在执行的协助可完成，不因新客到来中途归还；调岗、召回和物理工位排他仍在推进前撤销。直接请求与候选共用授权，恢复只验证当前权限及租约，不重演过去的优先级决定。
- `batch_transfers`仅合并已授权的生产送料、补货或自取备餐，各类别分别合并，目标容器及放料工时必须相同。候选保留稳定优先级，逐份保留来源、原owner、allocate_owner和取料工时；员工容量、目标空间与有限源可用量共同限制整组。
- 独立生产份数可共用一次搬运；`exclusive`仍禁止混不同订单，同单主餐/配餐可合并。显式terminal必须整份搬运，不与普通送料混组；多个图节点只引用同一bundle及各自的唯一child claim，不增加库存或运行状态账本。
- 拿取前不画手持，逐份实际拿取后增加手持，整组放下后清除。部分拿取取消经同一事务归还全部；保存恢复交叉验证所有图节点与每条child claim，不允许缺失、重复或额外绑定。

三家开发期真实模板均开启批量搬运；第三店前台另配置后厨搬运协助与接单留守。本节配置仍未接入正式ShopRules、UI或玩家旧档。

## 保存边界

### U05中的场景显示接入

```gdscript
var view := ShopView.new(owner)
var error := view.bind_runtime(runtime, displays, geometry)
var frame := view.render_snapshot()
```

绑定要求同一owner且展示定义有效，失败保留先前来源。公共帧使用presentation_version=1，包含实际stock/held/machines/draws、员工姿态和movement.customers；员工held_items与carry_count只来自真实手持lot，多个种类各画一张图。员工卡、机器面板、座位牌及活动统计复用公共来源；钱包、购买和全局属性继续由原外层持有。旧job/steps/timer不进入公共姿态，加工进度不从旧机器字典推算。调用或修改快照都不移动角色、不提交库存、不抽随机数。

公共场景只消费draws及权威顾客路径/抵达；等待库存没有默认图片，桌面餐品也需显式展示能力。旧堂食组件在此协议下只管理家具/占用，不自动创建第二份食物或顾客。混合拿取和取消复用原Actor、ItemArt与库存事务，不引入场景物品账本。

这仍是U05的显式显示接入点。正式ShopSession/ShopRules及存档未绑定它；开发期场景验收停止旧场景_process，只推进Runtime。不要在继续旧经营循环的同时绑定新显示，把两套状态并行当成正式集成。U06将由统一控制器接入唯一推进、命令和存档。

三份真实模板已声明各自需要的presentation，三份真实场景已完成公共姿态、手持、机器/座位信息、货架计数、货架/传送/用餐和等位的完整验收。第三店共享饭与装盘台出品默认仅计入UI，不生成散落图标，旧显示断言已替换。U05已完成，默认正式入口仍待U06切换。

### 显式展示与自动运输

SpecShopTemplate.presentation支持stock、counters、dining、poses和conveyors。stock可将多个容器合并到一组有限展示端口，counters从同一库存按容器汇总；dining只展示真实就座、eating且顾客容器中确有的餐品，消费后消失。poses声明座位或等位垫的端口、偏移和朝向，conveyors声明自动运输路线的显示路径。场景提供geometry={ports:端口坐标字典,hosts:排序宿主路径数组}，ShopPlay.bind_runtime负责从实际场景收集；缺端口或宿主时拒绝绑定并保留原显示源。投影不推进任何时钟或修改库存。

SpecShopTemplate.transports声明路线的from/to/connection/seconds/interval/capacity，transfer节点通过transport引用它。连接未购买时仍由员工执行相同节点；购买后由Runtime.step中的公共自动携带者执行。它复用Inventory的bundle/claim和hand@conveyor:<id>容器，保存的仅是路线冷却与在途bundle引用/剩余时间；取消、恢复及图节点绑定交叉验证不会复制物品。奶茶现有seal_to_shelf沿用3秒运输、1.5秒间隔与单次1份，不用显示动画替代真实搬运。

customer_movement.sync_records消费统一中性intent，先校验全部请求再更新目标、路径和离场。旧三种模式记录只在legacy/customer_intents.gd转换，兼容sync暂供旧正式入口使用；公共Runtime的顾客继续由Customers和RuleMovement持有，显示只消费其快照。U06必须移除旧调用路径，不能同时推进两套顾客状态。

快照包含无对象引用的状态；恢复先验证全部候选再采用。生产图、机器、库存、员工动作、路径、权限、补货引用和交付凭据各有交叉校验。

服务快照同时交叉校验生产份数绑定、接单员工租约、履约整组、顾客手持、目标与座位、用餐消耗凭据和动态顾客容器。接单、生产、员工取货、顾客携带、用餐五个阶段的恢复与连续运行对照一致。失败采用不修改原员工或服务。

这是开发期的新内部格式，尚未写入正式玩家存档。正式ShopSave仍需旧三种模式的转换、原字节备份、全局财务/名册整合和内容采用。公共钱包仍只由外层持有一次，服务快照不复制钱包；测试明确独立恢复外层财务后再恢复服务，不能将其当成已完成玩家存档迁移。

## U06：正式入口、旧档与兼容边界

三份正式 `shop.tres` 显式引用各自的 `shared_production.tres`。普通 ShopRules 构造、ShopSession、ShopPlay 自动使用唯一公共 Runtime；无需界面额外注入，视图在读档替换 Runtime 后跟随当前所有者。`content/examples/modular_shop.tres` 用同一入口复用第三店的声明能力与场景，使用独立 ID 和存档文件，不进入正式关卡表。

业务状态版本为 2：`template` 保存模板内容身份，`outer` 保存钱包、购买、名册元数据、修正器、RNG、提示历史等，`runtime` 保存唯一库存、机器、生产图、订单、顾客、活动员工与事务。旧 top-level stations/orders/serve/belt_items 不再写入正式存档。数值内容刷新保留在制机器的已提交配比与剩余时钟，新工作使用新定义；结构不兼容和不支持的未来版本保留原文件并返回具体错误，不静默清空进度。

`legacy_adoption.gd` 仅在旧档加载边界识别 handoff/single/serve。旧ID、现金、购买、岗位、库存归属、实际手持、加工/人工剩余时间和RNG转换成公共事实、claim与程序，再通过普通版本2恢复校验后整体采用。旧移动记录缺失时先恢复中性运动数据；自动运输保留在途时钟，旧顾客返座不提前扣用餐时间。文件替换前必须复制并逐字节校验原档，备份失败不能覆盖。

正式推进不再调用旧模式tick、动作context实例、旧机器/搬运副作用。旧状态验证仍只读使用历史协议的形状与静态动作计划；历史执行参考完整隔离在 `tests/fixtures/legacy_shops/reference_rules.gd` 与配套 reference_save 中，生产源码不导入它们。旧显示回退只供显式历史夹具，正式场景恒定消费 presentation_version=1 的公共帧。

命令与整帧推进以公共事件批次提交。到店、接单、流失和销售事件来自同一服务事实；销售在整单真实交付后广播，含订单/客人/餐品/数量/收入，提前付款也不会提前广播交付。回调可以保存、读档、召回；取消仍走公共库存补偿。奖励客流也通过公共 flyer 调度入场，受同一人数上限校验；奇遇先提交全部效果再广播外部回调。

U06验收见 `docs/qa/unified-shop-template.md` 最新章节。U07制作门禁和总验收仍独立待办；本阶段没有调整人物属性、速度、价格、客流、完店门槛或美术布局，没有替代完整经济/最终时长标定。
